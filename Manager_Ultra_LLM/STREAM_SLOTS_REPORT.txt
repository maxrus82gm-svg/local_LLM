P0 — КОНТРАКТ И ПОВЕДЕНИЕ

Маршрут: browser /api/chat/stream → Client /v1/chat/stream по проверенному TLS →
Manager /v1/chat/completions с stream=true → локальный Colibri SSE.
Manager и Client отдают NDJSON немедленно с flush; для потоковых сокетов TCP_NODELAY.
Hot path больше не собирает полную сводку RAM и всех слотов: проверяется выбранный
listener, /health, /models и повторно его идентичность. Полная сводка остаётся в overview.

События meta, reasoning, delta, done, error различаются явно. Для v2 reasoning и delta
имеют общую возрастающую sequence. Внутри SSE delta сохраняется порядок полей JSON;
между событиями — порядок upstream. Reasoning отображается в отдельной сворачиваемой
панели и хранится в reasoning_content; текст ответа остаётся отдельно. Reasoning-only
завершение допустимо, если его фактически выдал провайдер. Синтетического reasoning нет.

Проверяются Manager/slot/model/instance, а при наличии model в SSE — и upstream model.
Управляемому экземпляру необходим UUID; API model ID также содержит этот UUID, поэтому
старый чат не перепривязывается к новому экземпляру с тем же именем модели.
Legacy listener имеет хеш нативной идентичности процесса и сохраняет старый ключ истории.
Legacy Colibri1 не получает права на STOP или автоматическое присвоение ownership.

Отмена обрывает только сокет соответствующего запроса, включая ожидающее чтение Windows;
сокет detach/close предотвращает последующее закрытие переиспользованного handle.
Обрыв без [DONE], неверная последовательность/идентичность, deadline и ошибка не считаются
успехом. Частичный обмен не записывается в историю, скрытого повторного запроса нет.
Успешный request_id воспроизводит сохранённый результат без повторной генерации;
конфликт того же ID с другим запросом отклоняется.

Reasoning исследован по установленному исходному Colibri openai_server.py, без inference:
поддерживаются enable_thinking, reasoning_effort, reasoning_content и include_usage.
Для семейства Qwen3-Coder/OLMoE отдельный thinking не поддерживается; actual capability
проверяется по движку, явно несовместимая настройка отклоняется. Это не утверждение
о фактическом reasoning конкретной запущенной Qwen3.6 или KAT: такой тест NOT RUN.
Auto не передаёт override; on/off и effort задаются пользователем. Возвращаемое
assistant reasoning сохраняется в контексте — возможная польза для prefix reuse требует
проверки на настоящем движке. Отдельный decode benchmark не выполнен.

Пределы разделены:
- Убраны навязанные max_tokens=512 и enable_thinking=False в Manager chat.
- Для конфигурируемого Manager runner убраны универсальные --ctx 2048, --ngen 256,
  --ram 10, --no-think и OMP_THREAD_LIMIT=2. Без явных review.launch действуют defaults
  движка. Исторический отдельный owner-run --colibri2 trial сохранён совместимым;
  его старые ограничители не являются политикой Manager.
- review.launch: context_tokens, max_output_tokens, cache_ram_gib, threads, thinking,
  load_timeout_seconds. Параметры валидируются; реальный max_tokens из /health не
  подменяется молча: превышение явного запроса возвращает ошибку.
- Manager chat.transport defaults: request_bytes=1048576, message_chars=131072,
  history_messages=128, history_chars=240000, response_chars=1048576,
  stream_bytes=8388608, timeout_seconds=300. Настраиваемые ceilings заданы отдельно
  в chat_settings.py; лимит SSE строки — min(stream_bytes, 1 MiB).
- Client: локальный запрос 1 MiB, новое сообщение 131072 символа, answer и reasoning
  по 1 Mi символов, поток 64 MiB, NDJSON frame 2 MiB, ожидание 330 секунд.
  Непотоковый ответ Client ограничен 8 MiB; control response — 256 KiB.
  Действует наиболее строгий предел цепочки; увеличение одного Manager не отменяет
  локальную защиту Client. Эти границы перечислены в UI и данном отчёте.
- Пользовательский контекст: по умолчанию 100 сообщений/200000 символов; настраивается
  до 1024/1048576. Это символы, не оценка токенов. Загружается максимум 1024 последних
  сообщений; окно UI — 100. Метаданные контекста относятся к загруженному окну.
  Сокращение наблюдаемо; история автоматически не удаляется. При слишком большом
  контексте для политики Manager запрос отклоняется, а не молча обрезается.

Измерения без приватного текста в логах: вход Manager, preflight, начало Colibri,
первый Colibri fragment, первое forwarding Manager, первый receive Client,
token-file read/TLS context/HTTP headers, Client profile/SQLite claim/history,
DOM update, double requestAnimationFrame как возможность отрисовки, завершение,
persist и total. Метка rAF не является измерением физических пикселей дисплея.
Локальные интервалы используют perf_counter/performance.now. Разность epoch timestamps
разных машин требует синхронизации часов и не выдаётся за one-way network latency.

usage берётся только от провайдера. Rate = provider completion_tokens / измеренное
окно upstream request, включая prefill; basis и window_ms опубликованы вместе с rate.
Если счётчика нет, rate отсутствует. Это не чистая decode tok/s и не догадка по символам.

P1 — СЛОТЫ, РЕСУРСЫ, ПРОЦЕССЫ

Существующий /v1/control дополнен add_slot и select; check/start принимают slot_id.
add_slot серверно назначает slotN и свободный порт в control.slot_port_range
(default 8001..8999), исключая 8000, 8443, порт Manager, уже назначенные порты,
слушателей IPv4 и IPv6. SQLite BEGIN IMMEDIATE и UNIQUE гарантируют отсутствие
дублирующих резервирований при конкурентных запросах. Свободность повторно проверяется
при START; создание слота само по себе порт не bind-ит и ресурс не резервирует.

Данные slots, selection/revision, slot_requests, risk_checks, model_checks находятся
в прежнем control.sqlite3. Namespace привязан к Manager/host/instance_root. Конфликт
конфигурации и реестра отклоняется. select использует expected_revision и запрещён
для активного/защищённого слота. Удаления слота или экземпляра через DOM/API нет.
Создатель получает сохранённый grant на свой слот; это не control_models. Отзыв
control_models/токена и ограничения моделей действуют отдельно. Совместное использование
динамического слота можно явно предоставить прежним механизмом allowed_slots.

Каждый instance имеет UUID, API model ID, runtime/session paths, state, logs, temp,
job и stop-event. Lifecycle mutex остаётся общим для конкретного слота/порта,
сериализуя конфликтующие запуски; это необходимо для безопасности. Веса общие read-only.
Нет утверждения о совместном размещении весов в VRAM или ускорении нескольких CUDA.
STOP требует владельца/роли/слота и проверенной process identity; чужой PID/Job,
подмена session, listener и неподтверждённый stop не освобождают слот.
Неоднозначные ошибки остаются в карантине ERROR; автоматического kill/adopt/retry нет.

RAM/VRAM оценки и необязательный job_limit_gib задаются отдельно для модели/режима.
10 GiB RAM — configurable warning; risk confirmation возможен только при серверном
allow_risk_ack=true плюс действующие права. Check выдаёт токен на 60 секунд, связанный
с owner/slot/model/mode; он одноразовый. Деградация RAM, изменение оценок или рост
pending reservations требуют новой проверки. Cancel confirmation ничего не запускает.
READY уже учтён в физической free memory; второй раз он не вычитается. STARTING и
непроверенные claims резервируются консервативно. Неизвестная actual telemetry,
несовместимый runtime/CUDA, недостаток VRAM, занятый порт и ownership не обходятся.
GPU telemetry использует только уже установленный System32/nvidia-smi, GPU 0.
Multi-GPU routing не реализован. KILL_ON_JOB_CLOSE и прочие OS ownership protections
сохранены и при отсутствии произвольного общего memory cap.

KAT-Coder V2.5 подготовлен через прежний доверенный профиль и structural/review
проверки. Новый download/install не выполнялся. Настоящая загрузка 41-shard модели,
проверка native runtime, peak memory и inference в этой задаче NOT RUN.
