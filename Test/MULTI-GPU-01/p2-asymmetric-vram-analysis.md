# MULTI-GPU-01 — WORK: асимметричные бюджеты VRAM (исследование)
Дата: 27.11.2026, UTC+05. Статус: OPEN / READ-ONLY ANALYSIS; не назначение новой задачи, не LIVE GO, не реализация.

## Наблюдение на WORK, релиз №165
KAT-Coder-V2.5-Dev-Colibri, slot1 CUDA Full, обе GPU (4070 Ti SUPER 16 GiB + 3060 Ti 8 GiB); nvidia-smi: 6521 MiB и 5768 MiB occupied, 55% и 36% utilization соответственно, снимок в ходе генерации. Это суммарное потребление устройств, не только модели. Настройки: budget 21 GiB, reserves 2/0 GiB, ctx 65536, RAM cache 10 GiB, chain true, rows 1024. Фактический запуск --gpu 0,1 --vram 5.8. Причина ограничения найдена, потолок модели и прирост скорости не установлены.

## Причина и точки изменения
- Manager_Ultra_LLM/cuda_profile.py, reserve_plan(): capacity_i = max(0, free_i - user_reserve_i - HEADROOM_GIB), HEADROOM_GIB=2; common=min(capacity_i); gpu_weight_cap_gib = floor(min(common, requested)*10)/10. Это намеренно консервативная защита, а не физическая квота. Большая карта теряет доступную ёмкость.
- Manager_Ultra_LLM/colibri2_runner.py: подменяет пользовательский --vram общим cap; повторно проверяет cap перед стартом. control_runtime.py и slot_registry.py участвуют в оценке/подтверждении политики.
- Локальные исходники Colibri 2.1.0, c/coli: строка 4046 описывает --vram как total, но переводит число в CUDA_EXPERT_GB. c/qwen36_tier.c строки 1005–1019: числовой CUDA_EXPERT_GB трактуется отдельно для каждого устройства. При auto/отсутствии числа — собственная оценка свободной памяти минус 1 GiB и G_reserve для каждого устройства. Строки 1173–1192 вычитают размещённый trunk из лимита экспертов. В этой копии исходников QT_MAX_DEV=8, default auto selection без списка — до двух GPU (строки 889–903); Manager передаёт явный список. Проверить пределы и соответствие фактически используемому qwen36.exe перед изменениями. QT_HOME=layer / QT_LAYER_SPLIT: возможные режимы размещения, не доказательство поддержки произвольного N или ускорения.
- Не подавать 21 как единый --vram: на данном пути это потенциально 21 на каждую карту. Не отключать защиту/не считать 24 GiB общей физически непрерывной памятью.

## Предлагаемое решение (для будущей реализации)
Сначала сверить исходники/хэш/сборку и все потребители CUDA_EXPERT_GB. Исследовать штатный auto на изолированном стенде (не гарантирует пользовательские резервы или общий бюджет); если нет совместимого безопасного интерфейса, добавить в движок версионированный типизированный per-device budget, с проверкой фактического free, сопоставлением UUID -> masked ordinal и обратной совместимостью. Manager формирует budget_i отдельно, учитывает ОС, пользовательский резерв, headroom, буферы/KV, общий бюджет; сумма выделенных плановых лимитов не превышает запрошенный бюджет. Runner передаёт только проверенные значения, сохраняет безопасный legacy fallback и явное предупреждение для неподдерживаемого бэкенда; повторная проверка и подтверждение привязаны к полному вектору, а не scalar. UI показывает requested/effective/observed по каждой GPU и суммарно. Не обещать 21 GiB реально доступных: даже при полностью свободных картах 16+8 минус резервы 2+0 и текущий фиксированный headroom 2+2 даёт теоретически максимум 18 GiB бюджета весов при этих правилах, до сторонних расходов. Смена headroom требует отдельного обоснования.

## Постоянное архитектурное правило
Neuropolis должен учитывать различия в семантике VRAM, способах offload и пределах GPU у каждой модели/движка (Colibri, будущий llama.cpp и другие); никаких общих предположений о group vs per-device. Проектировать для N устройств, в том числе 1/2/3/4/5 GPU, разной ёмкости/скорости, занятых и исчезающих GPU; ограничения движка отражать как capability, не скрывать. Несколько независимых моделей: сохранять изоляцию групп; shared GPU quotas остаются отдельной задачей. Нельзя обещать линейный рост токенов/с с числом GPU или объёмом памяти.

## Приёмка будущей реализации
Синтетические тесты 1/2/3/4/5 карт (асимметрия, порядок UUID, занятость, invalid/zero budget, restart recheck, устаревшее подтверждение, неподдерживаемый runtime, отдельные слоты). Реальный WORK: KAT и Qwen, 4070 solo vs обе карты, одинаковый prompt «Морской бой», контекст/параметры, TTFT, prefill/decode tok/s, пик per-GPU VRAM, стабильность, освобождение после Stop; HOME — single GPU regression. Сверить allocations и логи движка, не только nvidia-smi. Не менять работающий runtime в ходе текущей генерации; исходники и main не изменены, тесты новой реализации NOT RUN. Интеграция Studio не требует завершения этого исследования; её собственные gates сохраняются.
