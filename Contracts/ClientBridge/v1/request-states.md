# Client Bridge v1 — request states (normative P0 candidate)

States: ACCEPTED, RUNNING, CANCEL_REQUESTED, SUCCEEDED, FAILED, CANCELLED, UNKNOWN.
Initial durable claim is ACCEPTED before dispatch. RUNNING means dispatch started, not proof of model token generation. Valid transitions:

- ACCEPTED -> RUNNING, CANCEL_REQUESTED, FAILED, CANCELLED, UNKNOWN
- RUNNING -> CANCEL_REQUESTED, SUCCEEDED, FAILED, CANCELLED, UNKNOWN
- CANCEL_REQUESTED -> SUCCEEDED, FAILED, CANCELLED, UNKNOWN (completion may win)
- SUCCEEDED / FAILED / CANCELLED terminal and immutable.
- UNKNOWN is an attempt-terminal/quarantined status: no automatic retry or new dispatch for this ID. Only authoritative late evidence may resolve UNKNOWN to SUCCEEDED/FAILED/CANCELLED; retain audit. It is never changed back to active. If no evidence, retain UNKNOWN.

FAILED requires a proven terminal failure, including admission/dispatch failure when no generation began. CANCELLED requires evidence of ended/non-started generation, not merely upstream receipt. A transport interruption, process crash, unverified cancellation or lost response without terminal evidence -> UNKNOWN. A disconnected SSE consumer does not imply cancellation succeeded. MVP attempts best-effort cancellation on disconnect, does not promise detached continuation or replay. Do not stop the model or Manager to cancel a request.

## Journal and admission

Bridge uses a protected durable SQLite journal keyed by (authenticated stable principal_id, WUA request_id). No full messages, prompt, reasoning, reply or Bearer secret stored in the Bridge journal. Store request digest, target_id, instance_id, correlation IDs if supplied, internal Manager request_id, state, timestamps, terminal evidence and available metrics. Request ID is 32 lowercase hex; Manager receives a separately generated 32-hex ID recorded before dispatch. Identity remains stable across token rotation; secrets not identity. A request ID is one execution attempt. Claim atomically before dispatch; unique slot admission and actual instance revalidation immediately before dispatch. Different principals cannot read/cancel/observe each other's requests. Treat another principal's request as unknown unless separately authorized (MVP no cross-principal access). Never expose Manager credentials.

Digest: SHA-256 of UTF-8 canonical JSON (RFC 8785 JCS) of the original validated ChatRequest excluding request_id and catalog_revision (revision is informational; all other fields including explicitly supplied options/correlation and messages participate). Do not normalize or truncate content; duplicate JSON object member names rejected. Equivalent key order gives same digest, omitted versus explicit option value is deliberately distinct. Same principal/request ID plus same digest -> 409 request_already_attempted; query status, do not dispatch again. Different digest -> 409 request_conflict, do not overwrite. Check an existing claim before checking current target readiness or instance, so restarts do not change duplicate semantics. Pre-claim validation/admission errors do not create an inference attempt; no automatic retries for ambiguous outcomes. Retain a durable tombstone (principal/request ID, digest, target, instance, terminal state/timestamps) after expiring detailed metrics; status still returns details_retained=false, no old output replay. Never age out identity in a way that permits accidental re-execution. Startup recovery marks unresolved active attempts UNKNOWN unless authoritative evidence proves terminal state; no automatic redispatch.

## Wire ordering

HTTP pre-admission errors are ordinary JSON responses (no SSE). After HTTP 200, if connection writable, first event meta sequence 0; then zero or more status/reasoning/delta/usage/telemetry/error, one final done event. Every data event has request_id and contiguous sequence (increment by exactly one). No event after done. error precedes done on FAILED/UNKNOWN, with matching code. SUCCEEDED/CANCELLED have null done.error. Journal terminal update before emitting done. If network EOF before done, consumer treats outcome as incomplete, queries status, never auto-reissues; partial output remains WUA-owned. Unknown may be recorded after stream loss even if done cannot be emitted. SSE comments heartbeat optional, not sequence events and not inference progress. Client-side timeout must be progress-based; heartbeat alone does not reset generation inactivity. No whole-answer buffering.

Cancel is idempotent: POST identifies exact original request/target/instance; different target/instance -> 409 stale_instance; unknown or other principal -> 404 unknown_request. For active attempt, record CANCEL_REQUESTED before forwarding mapped Manager request_id. Return current state, cancel_accepted=true only if cancellation intent durably accepted (can remain true on repeat); stop_confirmed=true only if CANCELLED is proven. For terminal success/failure/unknown, no new cancellation dispatch, return state and flags reflecting original accepted intent, never claim stop confirmed. Race with success yields SUCCEEDED. Cancel receipt and status never include generated content.

HTTP errors: 401 unauthorized, 403 forbidden (scope), 400 invalid_request incl malformed JSON/non-user final role, 404 unknown_target/unknown_request, 409 stale_instance/target_not_ready/slot_busy/request_conflict/request_already_attempted, 413 request_too_large, 422 unsupported_capability/context_limit/output_limit, 503 manager_unavailable, 500 internal_error. retryable is advisory for a new deliberate action after checking status; never authorization to auto-retry an existing ID. Post-admission error events map upstream failures to bounded stable codes; include sanitized upstream_code only, no raw stack trace or secrets. No fabricated cancellation/usage.
