# 20 — MCP-обращения к Unreal Engine: инструменты, сценарии, оптимизация запросов

**Дата фиксации:** 17.11.2026  
**Статус:** DESIGN NOTE / PROPOSED — концепция, не реализованная интеграция и не разрешение на её запуск.  
**Проект:** Ultra LLM / Colibri; будущая интеграция с Web Alarm Ultra / Blueprint LLM (архитектура №03).  
**Задача документа:** сохранить идею из голосового обсуждения: как LLM узнаёт и вызывает инструменты Unreal MCP, как уменьшить число поисковых запросов и объём контекста, как дать небольшой модели (например, KAT-Coder) проверенные маршруты действий.

## 1. Ключевая идея

Разделить три уровня:

1. **Исполняемые инструменты Unreal MCP.** Реальные операции редактора: найти Blueprint, получить граф, создать ноду, соединить пины, скомпилировать. Описание инструмента само по себе ничего не выполняет: за ним стоит реализация через API/плагин движка.
2. **Библиотека навыков/сценариев.** Проверенные маршруты из нескольких инструментов для типовых задач («поставить компонент», «добавить обработчик события», «изменить Event Graph», «создать Interface и подключить его к персонажу»).
3. **LLM-агент (KAT, Qwen, другая модель).** Понимает намерение пользователя, выбирает маршрут, заполняет параметры, получает обратную связь и при необходимости исправляет ошибку. Модель не обязана держать весь Unreal API в памяти.

**Не путать:** справочник = сведения о возможностях; инструмент = описание, схема аргументов **и работающий обработчик**; сценарий = последовательность инструментов; агент = логика выбора и корректировки действий.

## 2. Как MCP предоставляет инструменты модели

Типовой обмен: клиент MCP запрашивает каталог → получает имена, текстовые описания и типизированные схемы аргументов → модель выбирает подходящий инструмент → клиент исполняет вызов через сервер → ответ/ошибка возвращается модели.

**Что действительно обнаружено в текущем Unreal (read-only, 17.11.2026):**

- Доступный MCP endpoint отвечал на стандартные `initialize` и `tools/list`.
- Снаружи опубликованы **три** служебных инструмента: `list_toolsets` («List all available toolsets with names and descriptions.»), `describe_toolset` («Get detailed information about a toolset including all tool names, descriptions, and input schemas.»), `call_tool` («Call a tool by name…»).
- `list_toolsets` возвращает группы инструментов, включая `editor_toolset.toolsets.blueprint.BlueprintTools`, ActorTools, ObjectTools, SceneTools и другие.
- `describe_toolset` для `editor_toolset.toolsets.blueprint.BlueprintTools` вернул **53** операции **в этой установленной конфигурации**. Это не фиксированное число для всех Unreal/версий/проектов.
- У групп есть описания и входные `inputSchema` / часто `outputSchema`. Следовательно, модель может сопоставлять намерение не только с названием, но и с **описанием действия, обязательными параметрами и типами результатов**.
- В предыдущем устном объяснении упоминалась схема из четырёх служебных команд. **Фактический ответ этой установки — три**, поэтому для разработки опираться на живой `tools/list`, а не на предположенную схему.

Параметры и доступность могут измениться после обновления движка, MCP-плагина или дополнительных toolset. До вызова нужно сверять реальную схему.

## 3. Реальный пример: как агент распознаёт `create_node`

Ниже — не выдуманная «магическая» команда, а краткая выдержка из фактического описания `editor_toolset.toolsets.blueprint.BlueprintTools.create_node`.

**Описание:** «Adds a new node to the graph».  
**Обязательные аргументы:**
- `graph` — ссылка на объект графа Unreal, JSON-объект с `refPath`;
- `type_id` — строковый идентификатор **типа ноды**;
- `pos` — координаты `{x, y}` (целые числа).

**Необязательный аргумент:** `declaring_class` — ссылка с `refPath`; используется для различения одноимённых типов нод.

**Результат:** ссылка на созданный `EdGraphNode` с `refPath`.

Как агент понимает, что нужен этот инструмент:

- Задача пользователя — **создать** ноду в графе, а не только прочитать объект.
- Текстовое описание инструмента прямо обещает добавление ноды в граф.
- Схема требует `graph`, `type_id`, `pos`; значит, сначала нужно получить граф и корректный ID типа ноды.
- В списке этой же группы есть `find_node_types` (поиск совместимых типов; описание предупреждает, что вариантов могут быть тысячи и запрос лучше делать узким), `get_node_type_pins` (пины типа ноды), `connect_pins` (соединение выходного и входного пина), `get_graph` (граф по имени), `compile_blueprint` (компиляция).

**Важно:** название «Set Visibility» — человеческое имя действия, а не подтверждённый `type_id`. Реальный `type_id` нужно находить через `find_node_types` в контексте конкретного графа, класса и пинов. Не подставлять его наугад.

## 4. Два маршрута изменения Event Graph

### А. Поштучное редактирование

1. Определить цель: выбранный Actor, явно названный Blueprint или новый ассет.
2. Проверить тип цели; если выбран Actor-экземпляр в сцене, определить, нужен ли **класс Blueprint** или изменение только экземпляра.
3. Получить нужный Blueprint и граф через `get_graph` (`graph_name`, например `EventGraph`).
4. Узко найти тип нужной ноды через `find_node_types`; изучить пины через `get_node_type_pins`.
5. Вызвать `create_node` с найденным типом, ссылкой на граф и координатами.
6. Соединить проверенные входы/выходы через `connect_pins`; задать значения другими подходящими инструментами при необходимости.
7. Выполнить `compile_blueprint`, проверить ошибки и фактическую структуру графа; отдельно проверить поведение в UE, если задача требует runtime.

Этот маршрут удобен для маленькой правки, локальной отладки или слабой модели с пошаговым контролем. Пропускать ненужные шаги, если контекст уже известен.

### Б. Пакетное редактирование графа через DSL

В том же `BlueprintTools` **фактически найден** `write_graph_dsl`. Его описание: «Populates a Blueprint graph with nodes from a DSL script and compiles the Blueprint». Также доступен `get_graph_dsl_docs`, возвращающий синтаксис DSL. Есть средство чтения графа в DSL.

**Потенциальная оптимизация:** вместо множества `create_node` / `connect_pins` передать согласованный фрагмент графа одним вызовом `write_graph_dsl`. Для исправлений полезно предварительно прочитать текущий граф.

**Ограничение:** это **не проверенный выигрыш по токенам или надёжности**. Для DSL нужна точная грамматика, проверка правильности графа и оценка риска затронуть существующие ноды. Первый опыт — только на копии тестового Blueprint, с сохранением исходника, сравнимым результатом компиляции и rollback.

## 5. Контекст «выделенного объекта» без привязки всех задач к выделению

Предлагается гибридный resolver контекста.

- Пользователь говорит **«на выделенном объекте…»** → система перед планированием читает текущее выделение в редакторе, сообщает модели тип, класс/Blueprint, доступные компоненты и релевантные свойства. Дорогие сведения (весь граф, все ноды) подгружаются только по необходимости.
- Пользователь называет **конкретный ассет или персонажа** → агент ищет его по имени/пути; выделенный Actor не подменяет явно указанную цель.
- Пользователь говорит **«создай Blueprint Interface, добавь Interact, подключи к персонажу»** → многообъектный маршрут: создание Interface → выбор/поиск Blueprint персонажа → внедрение интерфейса и реализация. Выделенный объект в этом случае не обязателен.
- Модель при любой задаче может **сама запросить дополнительные данные** через MCP, когда предзагруженного контекста недостаточно.

**Семантика:** «выделенный» — предпочтительная привязка цели, а не режим, запрещающий обращаться к другим ассетам. Не использовать выделение молча, если пользователь имел в виду явно названный другой объект.

Перед **каждой записью** перепроверять ссылку на цель и актуальность выделения/ассета. Если выбор изменился или найдено несколько одинаковых кандидатов — остановить запись и уточнить цель. Чтение контекста не является разрешением на произвольное изменение проекта.

## 6. Оптимизация запросов и расхода контекста

**Базовое правило:** искать сначала минимальную нужную информацию, а не вставлять в prompt каталог всей системы.

- На входе в сессию сохранить **короткий индекс групп** (имя, назначение, версия/отпечаток каталога).
- По намерению запросить **одну релевантную группу**, затем извлечь **конкретные описания и схемы** инструментов, а не передавать модели весь большой JSON toolset.
- Для частых операций подготовить **карточки навыков**: триггеры, предусловия, необходимые вызовы, входные/выходные данные, проверки, типовые ошибки, fallback.
- Кэшировать только безопасные метаданные инструментов с привязкой к версии Unreal/плагина и сбрасывать кэш при изменении реестра. **Данные выделения и содержимое графа — динамические**, кэш без проверки может стать неверным.
- По возможности использовать **пакетный инструмент** или ограниченную оркестрацию вместо десятков отдельных шагов, но только после подтверждения эквивалентности и безопасности.
- Устанавливать лимиты числа попыток, вызовов и возвращаемых нод/строк; длинные ответы фильтровать до релевантной части; полный оригинал хранить отдельно в разрешённом хранилище, если он нужен для аудита.
- Измерять фактические `input/output/reasoning` токены и количество вызовов там, где провайдер/движок это отдаёт; ориентировочные оценки не считать реальными измерениями.

**Для локальной KAT:** короткие структурированные навыки, точные схемы и проверка каждого результата лучше непроверенных догадок об API. Но навыки не гарантируют правильное проектирование сложной Blueprint-логики. Отдельно тестировать способность модели понимать задачу, выбирать инструменты, контролировать ошибки и корректно завершать работу.

## 7. Пример навыка: «Set Visibility в Event Graph»

**Триггер:** «На выделенной лампе добавь Set Visibility для компонента …».

**Предусловия:** выбран ровно один подходящий Actor или указан Blueprint; есть нужный компонент; пользователь подтвердил, какую видимость и на каком событии изменять, если это не следует из задачи.

**Маршрут:** получить цель → Blueprint-класс → EventGraph → найти Set Visibility в контексте типа компонента → определить пины → добавить ноду (или использовать проверенный DSL-шаблон) → подключить исполнение и Target → компиляция → перечитать затронутый граф → сообщить, что сделано.

**Ошибки и защита:** отсутствует компонент, название совпадает у нескольких типов, неправильный Target, stale selection, несовместимые пины, compile error, изменена не та Blueprint-копия. При ошибке не утверждать «готово».

## 8. Норматив безопасности будущего агента

- Инструменты, меняющие проект, вызывать только в рамках явной пользовательской задачи; опасные массовые изменения и удаления — с подтверждением.
- Перед пакетной модификацией иметь сохранённую версию/Undo или проверенный откат; затем сравнивать результат.
- **Нельзя** считать успешный ответ MCP гарантией компиляции или правильного поведения в Play In Editor: есть отдельные уровни `MCP OK → COMPILE PASS → RUNTIME PASS → OWNER UX PASS`.
- Не давать небольшой модели произвольное исполнение Python/C++ или доступ к файловой системе только ради «оптимизации»: применять allowlist инструментов, проверку аргументов, границы проекта и разумные лимиты.
- Для Agent/Client/Manager/Web Alarm Ultra соблюдать раздельную авторизацию и действующие запреты на изменение LIVE инфраструктуры. Этот документ **не запускает** новый MCP, не разворачивает Client/Manager, не меняет Unreal-проект.

## 9. План последующей проверки (не назначенная задача)

1. Снять read-only каталог выбранного Unreal MCP и зафиксировать версию плагина/схемы.
2. Создать 2–3 карточки навыков: Selection → Component; Event Graph → `create_node`; Interface → Character.
3. На **отдельном тестовом** Blueprint сопоставить поштучный путь и `write_graph_dsl`: число вызовов, размер контекста, время, ошибки, compile, проверка изменений.
4. Прогнать один и тот же сценарий на KAT и более сильной модели при одинаковом доступе к инструментам и одинаковых критериях приёмки.
5. Только по результатам выбрать, какие навыки оставить инструкциями, а какие превратить в высокоуровневые MCP-инструменты.
