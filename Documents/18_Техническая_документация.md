Пункт запускает `ULTRA-CONTROL.py start --switch --model <профиль>`: сначала **валидация нового профиля и файлов**, затем корректная остановка **только текущей управляемой сессии**, затем старт новой. Само меню не сканирует GGUF, не импортирует модель и не создаёт её профиль.

Подробности эксплуатации и команды — `..\Colibri\ULTRA-README.md`; это справка **к существующему контроллеру**, не самостоятельная инструкция по добавлению LLM.

### 18.3.2. Проверка GGUF до импорта

- Установить точную модель, версию, репозиторий-источник, формат, квантование, лицензию, число файлов/shards и физический размер.
- Убедиться, что исходные веса целы хотя бы по размеру и заголовку; для полноценной проверки сверить SHA-256 с доверенным источником. GGUF обычно начинается с `GGUF`; идентифицировать `general.architecture` **из metadata**, а не по имени файла.
- Сверить выбранную архитектуру с **установленной версией Colibrì**, `Colibri\docs\gguf.md`: пример `qwen35moe` для Qwen3.6 MoE → `qwen36.exe`, `qwen35` для Qwen3.8 dense → `qwen36.exe`, `qwen4exp` для Qwen3.8-Flash-Next → `qwen38.exe` (наличие последнего на сервере **пока не подтверждено**).
- Не считать поддержку в исходном коде доказательством наличия соответствующего собранного CUDA/Vulkan/CPU runtime на сервере.
- Проверить сохранность предыдущих моделей и свободное место, RAM/VRAM; для Flash-Next с файлами порядка десятков ГБ особенно учитывать затраты стриминга SSD.

### 18.3.3. Импорт обычного одиночного GGUF без дублирования весов

**Только локально на сервере**, в `cmd.exe`:

```bat
cd /d "C:\Server\Ultra_LLM\Colibri"
py -3.12 -B c\coli import "C:\Server\Ultra_LLM\Base_LLM\Models\<МОДЕЛЬ>\<ФАЙЛ>.gguf" --out "C:\Server\Ultra_LLM\Base_LLM\Models\<МОДЕЛЬ>\<МОДЕЛЬ>.colibri" --mode link --no-mtp
```

Здесь `<МОДЕЛЬ>` и `<ФАЙЛ>` — **заполнители**, их надо заменить реальным названием. Указанный `--no-mtp` — вариант для наших текущих текстовых тестов без дополнительной MTP-головы; если у другой модели нужен MTP, подобрать правильный вариант по документации. `--mode link` создаёт компактную папку описания, веса остаются на прежнем месте. **Не использовать `--mode copy`, если не нужна отдельная физическая копия.**

После импорта проверить `*.colibri\config.json`, `gguf.json`, `tokenizer.json`; `gguf.json` содержит `format=colibri-gguf-v1`, `mode=link`, `arch`, `parts`, `size` и `gguf` с **локальным путём сервера**. Для многосоставного GGUF использовать официальное правило импорта первого файла, проверить все shards; не склеивать части вручную.

Существующий каталог `*.colibri` автоматически не переписывать. Импорт, `doctor`, `plan`, `serve`, проверка API и реальная генерация — **отдельные стадии**; один успешный импорт не означает, что модель отвечает.

### 18.3.4. Как добавить пятую или следующую модель в меню

**Перед правками** создать резервные копии `Colibri\ULTRA-CONTROL.py`, `ULTRA-SELECT.bat`, `ULTRA-README.md` и тестового модуля `Documents\Reports\CODEX-ULTRA-LLM-COLIBRI-START-001\test_ultra_control.py`. Уникальный суффикс резервных копий — дата и идентификатор модели; не перезаписывать старые.

**1. Профиль в контроллере.** Добавить отдельный ключ в `ULTRA-CONTROL.py` → `PROFILES`, не подменяя предыдущие:
```python
"newmodel": {
    "name": "Real-Model-Name",
    "folder": "Real-Model-Folder",
    "subfolder": "Real-Model-Folder.colibri",  # только для link-импорта GGUF
    "engine": "confirmed_engine.exe",
    "model_id": "unique-api-model-id",
    "ram": 32, "ctx": 8192, "cap": 8, "wait": 900
},
```
Это **пример структуры**, а не безопасные реальные параметры любой модели. `ram` — бюджет Colibrì, не ограничение всей оперативной памяти Windows. В проверяемом контроллере интервалы: RAM 4–64 ГБ, ctx 512–16384, cap 1–128.

**2. Инспектор и исполнение.** Добавить проверку геометрии, `model_type`, `GGUF arch`, числа тензоров, источника, длины файла, layout, tokenizer через отдельную функцию `inspect_<model>_gguf()` и подключить её в `inspect_model()`. Учесть `select_profile()` и `previous_profile()`. Для нового движка проверить `KNOWN_ENGINE_NAMES` и путь/подпись исполняемого файла. Проверить `plan_run()` — RAM, ctx, CUDA/Vulkan DLL, MTP, отдельные heat/usage histories, API ID. **Отказ при ошибке должен происходить до STOP текущей сессии.** Не присваивать новому файлу чужую идентичность, чтобы обойти проверки.

**3. Видимый пункт в `ULTRA-SELECT.bat`.** Для новой пятой модели (до этого есть четыре, `5 = Cancel`), заменить именно участок текущего меню на:
```bat
echo 5 - New model name
echo 6 - Cancel
echo.
choice /C 123456 /N /M "Select [1/2/3/4/5/6]: "
if errorlevel 6 goto :cancel
if errorlevel 5 goto :newmodel
if errorlevel 4 goto :qwen36
if errorlevel 3 goto :qwen38
if errorlevel 2 goto :kat
if errorlevel 1 goto :qwen
goto :cancel
:newmodel
set "ULTRA_MODEL=newmodel"
goto :run
```
В этом фрагменте **строки пунктов 1–4, существующие метки и общий `:run` остаются**; пример показывает лишь изменённые строки и ветвления, не полную замену файла. `if errorlevel N` означает «N **или выше**», поэтому порядок **строго по убыванию**. Четвёртый пункт уже занят Qwen3.6. Для нестандартного числа пунктов проверять ограничения символов `choice`.

**4. Проверки.** Внести тесты нового профиля: правильный API ID/путь/параметры; неверный source/geometry/header; отказ до STOP; переключение и восстановление последнего профиля. Выполнить полный офлайн набор, сверить прежние модели. Затем владелец запускает BAT **на сервере**, проверяет `READY`, `/health`, `/v1/models` и то, что выбран именно новый ID. Проверить CUDA, RAM/VRAM, скорость токенов, первую и вторую реальные реплики, после этого давать МАЯК-47.

**5. Завершение.** Отчёт в `Documents\Reports` (с PASS/FAIL/NOT RUN), актуализация списка моделей, №13, №14/15 и одной карточки на модель, если состоялся benchmark. **Удалять старые веса разрешается только отдельным решением владельца.**

### 18.3.5. Диагностика Colibrì и откат

Запускать **на сервере**:
```bat
cd /d "C:\Server\Ultra_LLM\Colibri"
ULTRA-STATUS.bat

```

- `--test` делает две **реальные** короткие последовательные генерации; требует запущенного READY API. Не заменяет МАЯК-47.

## 18.4. Ollama — альтернативное подключение

**Когда использовать:** отдельная проба моделей, диагностика совместимости, если Colibrì не поддерживает конкретную архитектуру, либо по решению владельца. Для текущего сервера Colibrì приоритетен. **Ollama и Colibrì не используют одно общее меню выбора; регистрация в Ollama не добавляет пункт в `ULTRA-SELECT.bat`.**

### 18.4.1. Проверка состояния и двух сценариев установки

На **сервере**, в PowerShell:
```powershell
ollama --version
ollama list
ollama ps
Get-PSDrive C
```

**Вариант A — скачать штатной командой Ollama** (только с разрешения владельца и при доступе в интернет):
```powershell
ollama pull <model:tag>
ollama run <model:tag>
```
Имена `<model:tag>` — заполнители, не реальные зарегистрированные модели. Применимость конкретной модели проверять по каталогу Ollama, расходу места и лимитам VRAM/RAM.

**Вариант B — зарегистрировать уже скачанный локальный GGUF.** В папке GGUF создать `Modelfile` с реальным абсолютным путём на сервере:
```text
FROM C:\Server\Ultra_LLM\Base_LLM\Models\<МОДЕЛЬ>\<ФАЙЛ>.gguf
PARAMETER num_ctx 4096
```
Затем на сервере:
```powershell
ollama create <unique-local-alias> -f .\Modelfile
ollama show <unique-local-alias>
ollama list
ollama run <unique-local-alias> "Ответь кратко: сколько будет 2 + 2?"
ollama ps
```

**Отдельное предупреждение:** `ollama create` может **копировать GGUF во внутренний blob-store Ollama**, расходуя повторно десятки гигабайт. Статус регистрации не доказывает работу инференса. Проверять свободное место **до** импорта; не запускать одновременно тяжёлую модель Colibrì, пока не подтверждён запас памяти.

### 18.4.2. Остановка и безопасное удаление дублей Ollama

- `ollama stop <unique-local-alias>` — выгружает запущенную модель из памяти, **не удаляя GGUF**.
- `ollama rm <unique-local-alias>` — удаляет **только конкретный зарегистрированный alias Ollama** и может освобождать невостребованные blobs; **не подменять** ручной чисткой `%USERPROFILE%\.ollama\models\blobs`.
- Перед удалением проверить `ollama list`, точный alias, отсутствие других зависимостей и убедиться, что Colibrì связан с **исходным** GGUF, а не с blobs Ollama. Факт освобождения диска подтверждать новым измерением, не расчётным размером.
- Любые операции `rm` и изменение общего хранилища — только после явного решения владельца.

### 18.4.3. Реальный кейс Qwen3.8 (01–02.11.2026)

- Источник: `Qwen3.8-27B-UD-Q6_K_M.gguf`, 23 088 409 504 байта.
- Пользователь зарегистрировал `qwen38-27b-q6km-local` через `ollama create` в Ollama 0.18.2; **регистрация прошла**, инференс **не прошёл**: HTTP 500 `qwen3next: layer 64 missing attn_qkv/attn_gate projections`. Это конкретная несовместимость версии Ollama и импортированного GGUF, **не** доказательство общей непригодности семейства.
- По подтверждённому консольному журналу владелец выполнил `ollama rm qwen38-27b-q6km-local`; после удаления `ollama list` был пуст, оригинальный GGUF и Colibrì link сохранились. Сравнение свободного диска: около 99 ГБ ранее → 110 ГБ после, но причинность и точный объём освобождённых blob-данных не установлены.
- Colibrì импортировала GGUF через `--mode link --no-mtp`, использовала только 64 базовых слоя, и пользователь получил реальную генерацию. МАЯК-47 R1 завершён и передан на независимую текстовую проверку (официальная компиляция UE5 не выполнялась). Сообщённая скорость 2–3 токена/с — **наблюдение владельца**, не профильный runtime-бенчмарк.
