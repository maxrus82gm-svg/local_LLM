# Архитектура

## Краткий срез — действующая архитектура, 11.11.2026

Ultra LLM — система многих Client и Manager. Каждый Manager управляет независимыми LLM, ресурсами и вычислениями своего сервера. Web Client подключает Manager, показывает предоставленные ими слоты и позволяет открывать отдельные чаты; количество моделей и разговоров не ограничивается фиксированным числом в интерфейсе. Сейчас один Manager объявляет три слота, но запущена только Colibri1/Qwen3.6. Ближайшая цель — настоящий обмен сообщениями и независимые чаты с возможностью открепления. Следом — мост к Web Alarm Ultra: Blueprint LLM смогут использовать ресурсы Client наряду с LLM, подключёнными непосредственно к Ultra. Новые движки, START/STOP, дополнительные регистрации и Интернет пока не приоритетны.

## Актуализация архитектуры — чаты, ресурсы Manager и мост к Web Alarm Ultra (11.11.2026)

**Решение владельца.** Реализуем уже согласованную систему, не расширяя сейчас набор движков и не подменяя практическую работу с чатами новыми экспериментами. Приоритет: **реальные чаты → независимые окна и проверка нескольких доступных LLM → мост к Web Alarm Ultra / Blueprint LLM → дальнейшее управление ресурсами и расширение**. Эта запись уточняет старую N:M-архитектуру, а не отменяет её. Старые подразделы ниже сохранены как исторические решения и результаты проверок.

### 1. Manager объявляет доступные экземпляры; Client не имеет лимита «три»

- **Manager** запускается на сервере с моделями и является единственным владельцем своей инфраструктуры: экземпляров Colibri, привязанных API, ресурсных политик, очередей, будущих lease и безопасных START/STOP. Его каталог может включать сколько угодно сконфигурированных слотов и экземпляров в пределах реально доступных CPU, GPU, RAM, VRAM, дисков и ограничений самих движков. Маленькие специализированные модели и мощные модели — равноправные будущие варианты; добавлять новые движки сейчас не требуется.
- **Client** подключает один или много независимых Manager, получает по проверенному защищённому каналу разрешённый каталог моделей и состояния слотов и **динамически** формирует список чатов. В текущем Manager объявлены три слота — пользователь должен видеть три соответствующих места для чата; четвёртый появится автоматически, если Manager действительно объявит четвёртый слот. В коде UI не допускается константа «не более трёх». Способ обнаружения Manager в сети пока не согласован; существующее явное подключение по доверенному HTTPS остаётся достаточным для первой версии.
- **Чат не равен экземпляру LLM.** Слот Manager — возможное место исполнения; экземпляр LLM — запущенный движок/модель; чат — отдельный логический разговор с историей и контекстом. У одной работающей LLM могут существовать несколько отдельных переписок; это не означает запуск дополнительных движков или выделение отдельного KV-слота на каждый разговор. Для адресации запроса необходимы Manager ID, slot ID, model ID и ID разговора; нельзя молча перенаправлять сообщения на другую модель.
- **Пустые и остановленные слоты** в интерфейсе видны честно как «не запущен» / «недоступен», а не как готовый собеседник. Отображение трёх пунктов не доказывает существование трёх одновременно работающих моделей. Клиент не запускает модель автоматически только потому, что пользователь открыл вкладку.

### 2. Независимые чаты и режимы работы

- В Ultra LLM Web Client нужна отдельная вкладка **«Чаты»** с выбором Manager / слота / модели, своей историей для каждого разговора и сохранением истории после закрытия окна. Чаты можно **откреплять в отдельные окна** и независимо общаться с несколькими LLM; это ожидаемая возможность самого продукта, а не три жёстко заданных страницы.
- Маршрут данных: **браузер → локальный Web API Client → авторизованный HTTPS Manager → локальный API выбранной LLM на сервере → тот же путь обратно**. Весовые файлы, KV-cache и сама генерация находятся на сервере. Client передаёт текст, историю/контекст в разрешённом объёме, метаданные и отображает результат; секретные токены Manager не передаются браузеру.
- Поддержать два пользовательских представления: **обычный запрос → готовый ответ** и **потоковый вывод ответа по мере генерации**. Дополнительное отображение хода рассуждения допускается **только если движок явно предоставляет отдельные данные для такого отображения**; ничего не имитировать и не считать режим рассуждения гарантированным для каждой модели. Лимиты, таймауты, отмена и ошибки сети — часть будущего проверяемого контракта.
- В будущем пользователь сможет отправить одинаковую задачу двум или трём доступным LLM и сравнить ответы, время первого токена, длительность, скорость и другие реально измеренные показатели на отдельных графиках. **Одновременная отправка не гарантирует одновременную генерацию:** Manager должен проверять доступные ресурсы и корректно ставить запросы в очередь или отказывать. Графики и автоматическое сравнение — развитие **после** первого реального чата, не препятствие для CHAT-01.

### 3. Web Alarm Ultra: Client — один из коннекторов ресурсов для Blueprint LLM

- **Web Alarm Ultra** должна иметь возможность через отдельный программный **мост к Ultra LLM Client** получать каталог доступных клиенту Manager/LLM и отправлять запросы выбранным моделям. Client является **одним источником** моделей для Ultra, не заменяет и не монополизирует её собственные подключения (например, будущий GigaChat или другие уже настроенные провайдеры).
- **Множество Blueprint LLM** смогут выбирать любой разрешённый ресурс из единого каталога Ultra: подключённую напрямую модель или доступную через Client → Manager. Blueprint отвечает за конкретную задачу, контекст и логику вызовов. Blueprint не обязательно жёстко закреплён за одной LLM: возможны последовательные либо, при достаточных ресурсах, параллельные обращения нескольких Blueprint к разным или общим моделям.
- **Разделение обязанностей:** Web Alarm Ultra — планирование, Blueprint-конвейеры, контексты, проверки и сборка результатов; Client — подключение Manager, каталог и маршрутизация; каждый Manager — разрешение операций, ресурсы и исполнение LLM на своей машине. Вся тяжёлая генерация остаётся у серверов; Client не превращается в вычислительный узел. Протокол Ultra ↔ Client, авторизация, потоковые ответы и отказоустойчивость требуют отдельного проектирования и согласования с репозиторием ag_llm. Историческую запись Documents/Ideas/IDEA-2026-11-11_Client_Gateway_WebAlarm_Ultra.md не переписывать задним числом; данное уточнение является текущим направлением **проекта Ultra LLM**, но не автоматическим изменением архитектуры ag_llm.
- **Приоритет после чатов:** как только настоящие сообщения на текущих LLM заработают, **не откладывать мост к Web Alarm Ultra ради новых движков, сложной регистрации или Интернета**. Готовящийся GigaChat внутри Web Alarm Ultra должен оставаться отдельным ресурсом, который Blueprint смогут использовать наравне с локальными Manager-моделями.

### 4. Фактические границы и ближайшая очередь

**Подтверждено к 11.11.2026:** один постоянно работающий LAN Manager и домашний portable Web Client, реальный HTTPS-мониторинг, три объявленных слота. Colibri1/порт 8000 с Qwen3.6 — ready; Colibri2/8001 и Colibri3/8002 — not_running. WEB-03 установлен, но сквозное одобрение нового клиента ещё не проверено. **Чат через Manager, серверный inference-proxy для Client, открепляемые окна, несколько одновременно отвечающих Colibri и коннектор Web Alarm Ultra пока не реализованы.**

**Непосредственно сейчас — CHAT-01:** сначала показать три динамически обнаруженных слота, отправить короткое реальное сообщение в уже запущенную Qwen3.6 из чат-окна Client и получить ответ. Затем независимые истории, открепляемые окна и последовательная проверка второго/третьего слотов **только после разрешённого безопасного запуска**. После успешной функциональной связки — первый мост Client → Web Alarm Ultra / Blueprint. Другие движки, дополнительные серверы, сложное обнаружение в сети, новые административные права, расширенный мониторинг, lease, START/STOP и Интернет не добавлять в качестве предварительных условий CHAT-01. Действующие Colibri1 и Valheim не останавливать и не изменять без отдельного разрешения.

## WEB-03 — доверенное подключение и одобрение Manager, gated rollout

- Новый Client создаёт уникальный токен исключительно в собственном ACL каталоге; Client Python отправляет по проверенному TLS только client_id и SHA-256, полученный Manager держит в ограниченной очереди **в памяти** (не пишет verifier до одобрения). Browser не видит токен. При перезапуске незавершённые заявки исчезают, Client может повторить.
- Manager проверяет фактический source IP **по TCP**, существующий allowed_client_ips и Firewall. Никакой саморегистрации с неразрешённого IP нет. Новые адреса требуют отдельного admin network decision; Интернет не открываем.
- Административная роль `pairing_admin` назначается только явной локальной владельческой операцией в защищённом Manager config; по умолчанию false. GET pending и POST approve/deny требуют индивидуальный Bearer и роль; новый Client никогда не может назначать себе роль. Доступные слоты выбирает админ; первые права нового клиента ограничены только просмотрами.
- Все существующие grant/revoke/set-role и новые Web approvals держат один protected config lock при полном read-modify-atomic-replace, чтобы не терять изменения при гонках. Сервис reload permissions на каждый запрос и не разрешает START/STOP.
- Новый Client status знает pending/approved/denied/expired по невредоносной квитанции и честно показывает offline при отсутствии доступа. Старые версии Manager сохраняют ручной резервный путь. Развёртывание живого сервера и админ-role не включены автоматически. QA local protocol без реального внешнего TLS, требуется отдельная LIVE-приёмка.

## WEB-02 — упаковка Web Client без зависимости от Python на целевой Windows-машине (11.11.2026)

**Engineering implementation:** standalone **onedir** Windows x64 пакет `UltraLLMClient.exe` + `_internal` (встроенный Python 3.12 и web_assets) + переносимые VBS launch/install scripts. Исходники Client и сборщик `Build-Portable.ps1` в репозитории; готовый ZIP собирается **вне Git** с контрольными суммами и Python License, без пользовательских secrets. Ярлык устанавливается для текущего пути папки: копирование на другой ПК требует повторного запуска `Install_Ultra_LLM_Client.vbs`.

Персональные `%LOCALAPPDATA%\UltraLLM\Client\{managers.json,*.token,*.pem}` **не включаются** в пакет и не переезжают вместе с ним. При первом запуске локальная программа создаёт защищённый каталог, открывает тот же Web wizard, при подтверждённом Manager разрешении показывает реальные данные через HTTPS. Автоматизация server-side pairing отдельная задача WEB-03, не механизм пакетирования. Сборка проверена на домашней Windows 11 x64 с `PATH` без Python, но ещё не испытана на другом физическом ПК. Менеджеры, ресурсы и последующие START/STOP (WEB-05/06) остаются server-side; упаковка не добавляет полномочий на сервере. Детали №18 §18.18 и Client README.

## УТВЕРЖДЕНО 11.11.2026 — только Web Client, запускатор и мастер подключения

- **Единственный целевой пользовательский интерфейс Ultra LLM Client — Web**, стилистика Web Alarm Ultra. Tkinter `live_client_gui.py` сохраняется только как историческая диагностическая утилита; дальнейших UI функций туда не добавлять. Старый `index.html` — не рабочая панель, а исторический макет.
- Тонкая локальная программа Client (Python, позднее упакованный .exe) по двойному щелчку запускает HTTP **исключительно на 127.0.0.1** (случайный порт), открывает браузер и проксирует запросы к каждому Manager по отдельному **верифицированному HTTPS**. Browser JavaScript не хранит/не видит токены, исходные конфиги Manager и файлы сертификатов; только публичные снимки ресурсов/состояний, принадлежащие клиенту.
- Первый запуск: Web-мастер спрашивает произвольное имя сервера, **Manager ID**, **Client ID**, IP/DNS и HTTPS-порт, импортированную копию публичного TLS сертификата. Client создаёт собственный секрет в защищённой папке профиля и выдаёт администратору лишь SHA-256 для регистрации; Manager должен отдельно разрешить `client_id`, слоты и IP. Прямое `IP:port` без доверенного TLS и авторизации не считается успешным подключением. Клиентские пути **никогда** не равны серверным путям Colibri/Models; клиенту они не требуются.
- Структура по-прежнему **N:M**, конфигурация каждого Manager-профиля отдельна, нет обязательного центрального сервера. Client установленный на любой разрешённой Windows-машине может обращаться к нескольким Manager. Публичный LAN/WAN локальный веб-сервер не открывает. Прямой браузер→Manager с клиентским токеном не применяется.
- Локальные файлы программы можно переносить; личные `.token`/`managers.json`/`cert.pem` остаются в `%LOCALAPPDATA%\UltraLLM\Client`, защищены Windows ACL и **не копируются с программой**. Ярлык создаётся заново для текущей папки. Фаза №1 требует локальный Python 3.12; автономный дистрибутив без Python — фаза №2.
- Менеджер остаётся единственным владельцем реальных слотов и процессов. Веб-кнопки START/STOP заблокированы до будущего атомарного admission/lease и безопасного server-side управления; нельзя имитировать запуск. Интернет (VPN/TLS) — позднее и только по отдельному решению.
- Реальный P1 Web Client `Client_Ultra_LLM/web_client.py` + `web_assets/` проверен с действующим `manager-server77` через домашний ярлык и локальный API. Это НЕ доказательство многоклиентной эксплуатации или переносимой no-Python сборки. План №04, история №09, техника №18 §18.17.



## УТВЕРЖДЕНО 10.11.2026 — многие Client ↔ многие переносимые Manager (N:M)

**Обязательная целевая топология:** любое число авторизованных Ultra LLM Client может подключаться к нескольким независимым Ultra LLM Manager; у каждого Manager может быть много клиентов. Каждый Manager устанавливается **на машине, где имеется Colibri и модели**, и отвечает только за свои независимые экземпляры, процессы, слоты, CPU/CUDA, RAM/VRAM и учёт резервов. Нет обязательного единого «главного сервера» и нет необходимости клиенту иметь SMB/WinRM-доступ к Colibri. Manager может обслуживать несколько разных моделей; клиент выбирает, к какому Manager обратиться. Не путать слоты менеджера с KV-cache слотом одного движка.

**Переносимость обязательна для обеих программ:** каталоги Colibri, моделей, runtime, адрес/порт и идентификатор Manager определяются конфигурацией конкретной машины, не жёсткими C:/S:/M:, hostname или IP в коде. Допустимо обнаружение установки лишь среди явно разрешённых каталогов, без слепого сканирования дисков и смены активной Colibri. Client хранит произвольный набор Manager-профилей с собственными endpoint, сертификатами и client credentials, не использует локальные пути сервера. Установка на произвольную Windows-машину — целевое свойство; пакетный installer пока НЕ создан.

**Статус для КОНКРЕТНОГО клиента:** список Manager содержит модели, реальные слоты и сведения о занятости, но доступность зависит от его авторизации, владельца слота, фактической свежей телеметрии, ресурсов и атомарных резервирований на данном Manager. Клиентское «свободно» — не гарантия: окончательный START/admission всегда выполняет Manager с OS-level lock/lease и перепроверкой, исключая двойное назначение одного ресурса двум клиентам. Ошибка связи, устаревшее состояние, неизвестная память/владелец => UNKNOWN/deny, а не обещание доступности. Резервирование между *разными* Manager локально независимо; координация/автобалансировка между ними — отдельный будущий этап.

**Сетевой маршрут:** первоначально защищённый LAN через HTTPS с проверкой сертификата, уникальной авторизацией клиентов и минимальными правами. Подключение через Интернет — одобренная будущая цель, **не текущий этап**; нужна отдельно согласованная защищённая схема (например, частный VPN или проверяемый TLS с авторизацией). Сейчас не открывать роутер и не публиковать WinRM/API наружу.

**Факт P1 на дату 10.11:** в `Manager_Ultra_LLM/live_manager.py` создан переносимый read-only HTTPS host; на DESKTOP-KT4G5SM код развернут отдельной копией в `C:\Server\Ultra_LLM\Manager_Live\live_manager.py` и действительно считывал Windows, `/health`, `/v1/models` работающей Colibri1 и локальный список моделей. `Client_Ultra_LLM/live_client.py` и `live_client_gui.py` поддерживают список Manager и HTTPS. **HTTPS-служба пока NOT STARTED, client→Manager ещё NOT VERIFIED** (защищённое создание/раздача credentials заблокировано в автоматизированном канале). Не объявлять P1 завершённой боевой системой, пока не проведена реальная сетевая проверка. Действующие 16 исходных файлов manager_dev, Colibri1 и Valheim не менялись; новый код не имеет команды START/STOP.

## Реализация UL-MGR-0D — текущая граница между макетом и серверной системой

В `Colibri/manager_dev` на серверном SMB после решений о multi-instance и постоянном серверном Manager создан **офлайн-компонент `service_core.py`** с тестами. Он компонирует предшествующий dry-run, планировщик и реестр слотов; принимает только ограниченные requests через injected-identity/telemetry и **не** слушает сеть, не устанавливает Windows Service и не запускает LLM. Суммарно 164/164 Python offline PASS на домашней машине (133 существовавших +31 новый), авторская самопроверка. Это **проектная внутренняя граница доверия**, не настоящая серверная аутентификация или API. Переход к production требует отдельного service host, безопасного server-side credentials/ACL, OS-level process ownership, mutex/durable leases/watchdog и независимых проверок. Существующая slot1/8000 и Valheim не изменялись. Оперативный статус/OPEN — №13, технические детали — №18, приёмка — №05/09.

## Утверждённая архитектура Ultra LLM Manager — 08.11.2026

**Владелец подтвердил схему по результатам сверки с Colibri UltraChat 03:** один центральный Ultra LLM Manager управляет **несколькими независимыми экземплярами Colibri**. Это не одна Colibri с несколькими KV-слотами. Один KV-слот — внутренний контекст/KV-cache одного движка; отдельный экземпляр — самостоятельные процесс инференса, API-порт, модель и состояние; слот менеджера — ресурсно управляемое место для экземпляра. Возможности нескольких моделей в одном gateway отдельно НЕ проверены и не заменяют принятое решение.

| Слот менеджера | Первоначальная роль | Серверный порт | Статус |
| --- | --- | --- | --- |
| slot1 / Colibri | Существующая, обязательно защитить | 8000 | Исторически запущена на CUDA; макет с пометкой CPU не доказывает нынешний backend |
| slot2 / Colibri2 | Первый новый CPU-инстанс | 8001 (план) | Dry-run принят, живой запуск НЕ выполнен |
| slot3 / Colibri3 | Следующий инстанс, первоначально CUDA | 8002 (план) | Только после CPU-gate |
| slot4 / Colibri4 | Возможное расширение | 8003 (пример UI) | CONDITIONAL, к запуску не утверждён |

**Менеджер (единственный, не создавать второй):** серверный registry и центральный авторизованный контроль моделей, atomic slot+RAM reservation для нескольких пользователей, учёт PID/creation time/parent/портов/владельца, раздельные setup-home/temp/cache/stop/lock/log, безопасные START/STOP только собственных процессов, измерения RAM/VRAM и отказ при UNKNOWN. Весовые файлы KAT-Coder V2.5/Qwen3.6 общие, дубли моделей не нужны. Режим CPU/CUDA должен определяться разрешённым профилем, а не навсегда именем слота. Начальная политика: **не более одной активной CUDA-сессии**.

**Клиентская архитектура:** лёгкий клиент Ultra LLM Manager на пользовательских ПК, централизованное исполнение на DESKTOP-KT4G5SM по будущему защищённому LAN API; визуальный стиль Web Alarm Ultra, но разделение ответственности: Manager — процессы/ресурсы/модели, Web Alarm Ultra — задачи/контексты/агентная логика; интеграция позднее. GitHub maxrus82gm-svg/local_LLM/Documents — документация, домашний M:\GitHub\local_LLM — её клон, домашний S:\Ultra_LLM — отдельная Colibri. Сервер локально C:\Server\Ultra_LLM, доступ к его ФАЙЛАМ с домашнего ПК по \\192.168.0.77\Server\Ultra_LLM; SMB не предоставляет серверный shell.

**Фактический прогресс:** в серверном Colibri/manager_dev существуют UL-MGR-0A/0B/0C, включая server_runner.py. 133/133 offline Python PASS независимо повторены на домашнем DESKTOP-SC96D3U; live Colibri2 START/STOP, два одновременно работающих CPU, CUDA slot3, API/LAN, OS-level ownership/durable leases/mutex/watchdog — NOT RUN/NOT IMPLEMENTED. Плановый budget 10 GiB/модель и резерв 20 GiB игровым службам + минимум 10 GiB свободной RAM требуют проверки без двойного вычитания занятых ресурсов.

**Порядок этапов:** 1) авторизованный server-side command path и CPU-runtime preflight; 2) достоверный учёт процессов/памяти; 3) OS-level locks, durable leases, auth, безопасная принадлежность PID и fail-closed STOP; 4) Colibri2 CPU по отдельному разрешению владельца; 5) проверка двух CPU; 6) Colibri3 CUDA после CPU-приёмки; 7) защищённый LAN-клиент и затем Web Alarm Ultra API.
