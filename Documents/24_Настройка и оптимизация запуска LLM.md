## 1. Настройки как независимые экземпляры

OWNER: все пользовательские параметры запуска должны быть доступны через интерфейс и сохраняться отдельно для конкретного Manager, модели, режима CPU/CUDA и слота/профиля. Не зашивать пользовательские значения в исходники, BAT или глобальные переменные окружения. Код содержит проверенную схему, допустимые диапазоны, адаптеры, безопасные defaults и алгоритмы, а не единственный набор параметров для всех компьютеров. Manager определяет аппаратные возможности своего узла и проверяет значения; Client редактирует разрешённые поля через авторизованный API. Studio получает capabilities/фактические параметры, не управляет драйвером самостоятельно.

Профиль — сохраняемый объект с ID и ревизией, выбранный слот получает собственный экземпляр настроек; активный процесс имеет неизменяемый снимок effective launch. Порядок наследования (предложение): default адаптера → профиль узла/модели/режима → явно сохранённые настройки слота → разрешённые параметры запуска. Изменение одного слота не изменяет другие. Различать default/inherited, desired, effective и observed; неизвестно ≠ 0. После сохранения показать, требуется ли перезапуск модели или Manager; только явное применение, без скрытых рестартов. Профили, их копирование/выбор и полный UI пока OPEN, не объявлять реализованными.

## 2. Карта параметров

| Параметр | Colibri 2.1.0 / текущий путь | Правило управления |
|---|---|---|
| Потоки CPU | launch.threads → OMP_NUM_THREADS, OMP_THREAD_LIMIT, OPENBLAS_NUM_THREADS, MKL_NUM_THREADS | CPU и CUDA: авто, максимум, максимум минус 2, ручное 1..доступных логических CPU; Manager учитывает affinity/лимиты ОС, показывает физические ядра, логические CPU, настроенное и подтверждённое движком число. OS thread count не равен числу вычислительных потоков. |
| RAM | --ram / cache_ram_gib | Бюджет кэша, не общий RSS; отдельно RAM экземпляра, доступная RAM узла, резерв. |
| GPU | --gpu, COLI_GPUS, CUDA_VISIBLE_DEVICES | Выбор физической GPU по UUID; masked ordinal передаёт адаптер. Auto/одна/Full/выбранные GPU; отсутствие поддержки явно показать. |
| VRAM | --vram → CUDA_EXPERT_GB; budget_gib, target_gib, gpu_reserves_gib | Раздельно суммарная цель, бюджет весов, резервы каждой GPU, вычисленный лимит и реально занятая память; target не квота. |
| Размещение | QT_HOME=layer, QT_LAYER_SPLIT, COLI_PLACE | По умолчанию штатный алгоритм; экспериментальный выбор только после проверки конкретного движка/модели. |
| Chain | COLI_CUDA_CHAIN, COLI_CUDA_CHAIN_ROWS | Вкл/выкл и число строк чанка prefill; 1024 — проверяемый профиль, не универсальный оптимум. Показывать requested и фактическую активацию/причину отказа. |
| Контекст | --ctx / context_tokens | Токены, не символы; включает вход и ответ, история/шаблон входят в вход. KV и scratch расходуют память отдельно от весов. |
| Генерация | --ngen / max_output_tokens, thinking и параметры sampling по capability | Отдельно от контекста; отсутствие искусственного потолка не отменяет лимит движка. Изменять только поддерживаемые параметры. |
| Телеметрия | engine health/logs, RAM, VRAM, WDDM | TTFT, prefill (tokens/s), decode current/mean, reasoning/answer, общее время; не смешивать end-to-end с decode. Dedicated VRAM и shared GPU RAM не складывать как физическую VRAM. |

## 3. Colibri: Multi-GPU и CUDA Chain

Проверенные источники upstream v2.1.0: [Qwen3.6 CUDA tier](https://github.com/JustVugg/colibri/blob/v2.1.0/docs/qwen36-cuda-tier.md) (разделы Two cards as a pipeline, The dense chain on the card, The routed experts in the frame), [CUDA backend](https://github.com/JustVugg/colibri/blob/v2.1.0/docs/cuda.md), [qwen36_tier.c](https://github.com/JustVugg/colibri/blob/v2.1.0/c/qwen36_tier.c#L1005-L1019), [CLI](https://github.com/JustVugg/colibri/blob/v2.1.0/c/coli#L4045-L4046). Сверять с реально установленной сборкой и хэшем EXE/DLL, не переносить семантику между движками.

- Общая документация GLM описывает CUDA_EXPERT_GB как общий бюджет, но в qwen36_tier.c число применяется отдельно к каждому устройству. Auto считает free минус 1 GiB и внутренний G_reserve. Auto может оставить часть экспертов на CPU при низкой скорости GPU; не гарантирует заданные пользователем резервы. CLI --vram 0 означает auto; строка auto не является числовым аргументом CLI.
- Наш текущий restricted профиль ограничивает все карты общим минимумом: cap_i=max(0,free_i-user_reserve_i-2 GiB); передаваемый scalar=floor(min(cap_i,requested)*10)/10. Это не аппаратная квота. 16+8 GiB при резерве 2+0 и headroom 2 на карту дают максимум 18 GiB весов даже при полностью свободных GPU. Реально меньше. Не передавать 21 как число каждой карте. Независимый вектор бюджетов нужен с проверкой суммы, UUID и повторным admission перед запуском; #168 — только прототип, не подключён к Manager.
- По умолчанию эксперты распределяются по eid % N в каждом слое; медленная карта задерживает синхронизацию слоя. QT_HOME=layer размещает экспертов по диапазонам слоёв с учётом ёмкости и измеренной скорости GEMV; QT_LAYER_SPLIT задаёт число слоёв первой карты только при N=2. Не обещать ускорение. QT_MAX_DEV=8 в исходнике, без явного списка выбирается до 2; N=3/4/5 требует проверки всех путей.
- Полный CUDA Chain Qwen3.6 требует все проекции, shared expert и lm_head на одной карте. Разнесение этих компонентов может выключить Chain; оптимизация routed experts in frame отдельно не поддерживает tier >1 GPU в этой версии. Поэтому режим по слоям сам по себе не восстанавливает Chain. Исследовать размещение trunk на быстрой GPU (COLI_PLACE по upstream), experts на выбранных устройствах, только проверенные комбинации. Нет доказанного универсального Multi-GPU ускорения.
- PCIe: измерять generation/width под нагрузкой, топологию, P2P и обмен CPU↔GPU; текущая скорость линии может меняться. Медленная карта может быть полезнее для независимого экземпляра другой модели, чем для одной общей модели. Не считать сумму VRAM непрерывной памятью.
