## Целевая программа N:M и практический LIVE-этап — решение 10.11.2026

**Принято владельцем:** произвольное число переносимых Manager на разных машинах с Colibri; произвольное число Client, каждый подключается к нескольким Manager по профилям. Менеджер автономно управляет только своей машиной, слотами и резервами. Клиентам показывать список моделей и персональную доступность. Нет обязательного главного Manager. Internet-access — будущий отдельный защищённый этап.

**Последовательность без имитаций:**
1. **Текущий P1 / PARTIAL:** отдельный реальный серверный код `live_manager.py`, фактический Windows/Colibri мониторинг подтверждён на DESKTOP-KT4G5SM; `live_client.py` и Tk GUI подготовлены. Завершить безопасную конфигурацию TLS/auth и подтвердить настоящий Client→Manager GET по LAN без открытия интернета.
2. **P2 / OPEN:** связать реальный клиентский запрос с внутренним серверным ядром `manager_core`/`service_core`; server-side identity, атомарное бронирование ресурсов на клиент, TTL lease, OS-level locks, отказ при UNKNOWN, многопользовательская конкуренция. Никаких гарантий по статусу просто «idle».
3. **P3 / OPEN:** по отдельному подтверждению владельца управлять стартом/стопом только собственного slot2 CPU через проверенные `colibri2_runner/windows_process`; защитить slot1 и Valheim. Проверить настоящее inference, ограничения RAM, откат.
4. **P4 / OPEN:** переносимый инсталлятор Manager/Client, выбор каталога/обнаружение Colibri только в заданных путях, защищённый pairing, несколько машин в LAN.
5. **P5 / FUTURE:** доступ к нескольким Manager через интернет по отдельно согласованному защищённому соединению (TLS, VPN, управление ключами). Никакого текущего WAN/firewall-open.

Подробности: №03 — архитектура; №06 DEC-006/007; №13 — текущий статус; №18 §18.12 — фактическая техника. Не считать этапы 2–5 автоматически разрешёнными.


**Назначение:** единый **план развития проекта**. Хранит согласованные направления, их последовательность, критерии готовности и зависимости. ## Как вести этапы

Для каждого этапа фиксировать: **ID / цель / статус (IDEA, PROPOSED, APPROVED, IN PROGRESS, BLOCKED, COMPLETE, DEFERRED) / решение владельца / зависимости / критерий завершения / TASK ID / evidence**. ## Новое направление 02.11.2026 — отдельные обращения к LLM и память в Ultra

**Идея владельца, не утверждённая реализация (IDEA / NOT IMPLEMENTED):** хранить историю диалогов и рабочий контекст в Web Alarm Ultra, а Colibrì / KAT / Qwen и другие локальные модели использовать по отдельному запросу (stateless-подобный режим). Перед обращением Ultra формирует ограниченный пакет контекста и отправляет его модели; после получения результата сохраняет в Ultra, не требуя бесконечной внутренней истории модели. Возможен вариант без долгой сессии чата; **не путать одноразовый запрос с перезагрузкой весов на каждый вызов** — загрузка 20+ ГБ каждый раз может замедлять работу, поэтому изучить два варианта: *однократный API-вызов к прогретой модели с внешней памятью* и *холодный запуск по запросу*.

**Причина гипотезы:** Qwen3.6 после 572-строчного ответа МАЯК-47 перестала отвечать на новые сообщения (со слов владельца), KAT в прежних прогонах такого не показывала. Источник причины не установлен: возможен Colibrì, движок, контекст, ресурсы или UI. **Не утверждать, что stateless-режим автоматически устраняет сбой**; отдельно проверить повторные запросы, длину контекста, token budgets, устойчивость API, восстановление после ошибки, ресурсный расход и аудит протокола.

**Уточнение архитектурной гипотезы по решению владельца 02.11:** Ultra становится **единственным хранителем диалоговой памяти, долгосрочных фактов и итогов**, собирает для каждого вызова только релевантный контекст в пределах окна модели. **Уточнение владельца:** после завершения задачи Ultra сначала сохраняет результат и нужные сведения в своей долговременной памяти, затем **закрывает/удаляет старый чат Colibrì и открывает новый чистый чат** для следующей задачи. Внутри движка не должна наследоваться история и состояние KV-cache старой логической сессии: фактический сброс/изоляцию KV-slot требуется проверить технически, поскольку одно удаление UI-чата может не очищать память инференса. **Сам Colibrì и загруженные веса остаются в памяти (warm), без остановки сервера или перезагрузки 22 ГБ на каждый запрос.** Ultra передаёт каждому новому чату ограниченный пакет собственного контекста, а не полную старую переписку. Требуются контроль повторного использования KV-slot, очередь/тайм-аут, health-check и безопасное восстановление при потере отклика. Новая сессия **не гарантирует** решения зависания, если проблема в движке, GPU или scheduler. **Критерии будущего этапа (не TASK):** Ultra ведёт историю, умеет сокращать контекст до окна модели, выбирает LLM, отправляет независимые запросы, принимает результат/ошибку с timeout и сохраняет результат. Возможность повторного обращения и восстановления оценивается отдельно. Никаких процессов, сетевых маршрутов или сервисов пока не изменяли. **Единая инструкция подключения Colibrì/Ollama** остаётся в `18_Техническая_документация.md`.
