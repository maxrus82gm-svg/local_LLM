# IDEA-2026-11-11 — Ultra LLM Client как шлюз моделей для WebAlarm Ultra

**Статус: IDEA / DEFERRED — только фиксация, НЕ утверждено к реализации.**
**Автор:** владелец проекта, 11 ноября 2026.
**Проект-источник:** Ultra LLM (local_LLM). **Где принимать решение:** WebAlarm Ultra (ag_llm).

## Суть предложения

Рассмотреть альтернативу прямому подключению WebAlarm Ultra к каждому Manager:
**WebAlarm Ultra → локальный Ultra LLM Client → несколько Ultra LLM Manager → локальные LLM.**

Пример:
1. Пользователь устанавливает переносимый Web Client на свой компьютер.
2. Client авторизованно подключён к нескольким Manager на разных компьютерах, на которых суммарно могут быть доступны, например, 6–7 LLM.
3. WebAlarm Ultra подключается к Client по согласованному локальному API и получает каталог доступных пользователю моделей, их возможности и актуальное состояние.
4. Blueprint-планировщик WebAlarm Ultra распределяет независимые подзадачи по моделям; Client маршрутизирует запросы к Manager.
5. WebAlarm Ultra собирает, проверяет и объединяет ответы; при необходимости используются облачные модели.

В дополнение предложено в будущем рассмотреть **простой чат в Ultra LLM Web Client** для ручной работы и тестовых запросов к LLM. Это отдельное необязательное предложение, пока не принятое к реализации.

## Выгоды и оговорки

- WebAlarm Ultra может интегрироваться с одной точкой вместо множества Manager; переиспользуются настройки подключения и права Client.
- Независимые задачи потенциально выполняются параллельно на нескольких компьютерах. Ускорение зависит от ресурсов, зависимостей, сети и затрат на объединение результатов.
- Локальные модели не обязательно требуют платного внешнего API за токены, но токенизация/инференс, электричество, память и вычисления никуда не исчезают. Облачные LLM тарифицируются отдельно.
- Client не должен обходить авторизацию, server-side lease/admission или управление процессами Manager.

## Вопросы для обсуждения в WebAlarm Ultra

1. Выбрать архитектуру: **WebAlarm Ultra → Client → Manager**, прямую **WebAlarm Ultra → Manager** или гибрид; оценить риски единой точки отказа.
2. Согласовать API каталога моделей, маршрутизации, streaming, отмены, лимитов, таймаутов, ошибок и учёта токенов.
3. Разделить роли: **Blueprint-планировщик, очереди и сборка итогов — WebAlarm Ultra; физические модели, слоты, резервы и START/STOP — Manager; Client — возможный шлюз**.
4. Проверить авторизацию и безопасность каждой связи; browser не получает секретов Manager.
5. Отдельно решить необходимость чата внутри Client.
