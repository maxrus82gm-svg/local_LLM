## 1. Рабочие правила Codex

1. **Источник работы:** только БЛОК 1 с задачей, назначенной владельцем, либо его прямое адресное поручение с указанными границами. План, NEXT, сообщение «можно будет» или отсутствие задач — не назначение. Поправки после назначения фиксировать как AMENDMENT с датой, не заменяя первоначальный текст.
2. **Вход:** изучить этот раздел, БЛОК 1, разрешённые источники из read matrix постановки, нужные узкие фрагменты `00_Старт.md`, `02_Назначение_проекта.md`, `03_Архитектура.md` и `13_Тактический_контекст.md` **только когда это прямо предусмотрено scope**. Не читать автоматически чужие карточки, общие архивы или весь реестр. Если источник недоступен — сообщить `SOURCE UNAVAILABLE`.
3. **Границы:** выполнять только перечисленные read/write/test-действия. Без отдельного разрешения не трогать Git/GitHub, системные настройки, работающие процессы/загрузки, модели и веса, сеть, чужие файлы и рабочее хранилище. Техническая доступность не означает разрешения. Особое согласование требуется для остановки загрузок и любых установок/удалений.
4. **Инженерный подход:** сначала установить существующее состояние, проверить переиспользование и соседние ограничения; выбрать минимальное достаточное решение. Делать проверяемые изменения, фиксировать подтверждённые факты и отдельно гипотезы. Не расширять TASK из-за попутной находки.
5. **Проверки:** выполнять оговорённые тесты в разрешённой среде, указывать команды/результаты и `PASS / FAIL / SKIP / NOT RUN`; для документации проверять содержимое, ссылки, отсутствие потерянных записей и граф Obsidian. Самопроверка Codex — доказательство исполнителя, **не** независимая приёмка.
6. **Сдача:** сохранить полный отчёт и, когда согласовано, manifest/evidence в постоянном разрешённом месте. Ответ в чате содержит `DONE / CHANGED / DIFF / PROBLEMS / QUESTIONS`, фактический статус, тесты, риски, DOC IMPACT, адрес отчёта и предложенный NEXT. Не выдавать черновик за завершённый отчёт.
7. **Приёмка и история:** ChatGPT-координатор отдельно проверяет результат, сохраняет полную исходную постановку и отчёты, заполняет персональную историю, общий реестр/хронологию и тактический контекст. Codex **не пишет себе independent PASS** и не изменяет личный архив.
8. **Сохранность:** после сдачи БЛОК 1 не очищать и не заменять, пока координатор не подтвердил архив, все AMENDMENT и повторное чтение. БЛОК 1.1 пока **ручной защищённый резерв координатора**, автоматической ротации и скрипта нет. БЛОК 4 — только для независимой оценки координатора.

### Среда Codex/Desktop — обязательная проверка путей

Codex работает **на компьютере владельца**, поэтому обращается к файлам Ultra LLM по сетевому корню `\\192.168.0.77\Server\Ultra_LLM` (например, к `Documents`, `Colibri`, `Base_LLM\Models`). Путь `C:\Server\Ultra_LLM` — локальный **на сервере**, не предполагаемый диск Codex. Он допустим внутри BAT, который будет исполняться на сервере, но файл BAT агент редактирует через UNC. Запуск BAT с UNC на компьютере агента не запускает его на сервере. Указать фактическую машину, путь, доступ, права, место выполнения и тестовый scope; если нет права удалённого запуска — `NOT RUN`. ## 1. Главная цель

Довести Ultra LLM до состояния, в котором пользователь:

1. Получает ответ в Client постепенно, непосредственно по мере генерации Colibri, без ожидания полного завершения.
    
2. Видит отдельно рассуждения модели, если Colibri фактически отдаёт соответствующие события.
    
3. Может сравнить скорость прямого Colibri и маршрута через Manager/Client; дополнительная задержка измерена и устранена там, где это технически возможно.
    
4. Видит каталог доступных моделей каждого Manager.
    
5. Имеет три начальных слота в текущей конфигурации, может добавлять новые кнопкой «+».
    
6. В каждом управляемом слоте выбирает модель, CPU/CUDA и запускает или останавливает только соответствующий собственный экземпляр.
    
7. Может одновременно запускать несколько одинаковых LLM в независимых экземплярах.
    

**Порядок строго обязательный: P0 STREAMING → P1 MULTI-INSTANCE/UI.**

Не начинать с переписывания архитектуры. Сначала переиспользовать завершённую офлайн-реализацию CONTROL-01, затем устранить недостающие функции.

## 4. P0 — главный этап: настоящий streaming и скорость

### 4.1. Проверка действующего пути запуска

Без изменения установленной программы проверить в read-only режиме:

- фактическую цель пользовательского `.lnk`;
    
- вызываемый VBS, EXE, рабочую папку и версию;
    
- источник локального Client API;
    
- какие компоненты есть в SOURCE, но ещё отсутствуют в LIVE;
    
- отсутствие второго параллельного Client, способного вводить пользователя в заблуждение.
    

Ничего не переустанавливать, не исправлять ярлык и не завершать работающий Client без отдельного разрешения.

Результат: таблица `SOURCE / INSTALLED / GAP`.

### 4.2. End-to-end поток

Добиться настоящей передачи фрагментов по маршруту:

`Colibri SSE → Manager → Client → Browser`

Требования:

- передавать фрагмент сразу после его получения;
    
- не ждать окончания полной генерации;
    
- не собирать весь ответ в Manager перед передачей;
    
- не буферизовать его целиком в Client;
    
- немедленно обновлять текст браузера при поступлении фрагментов;
    
- корректно обрабатывать разбитые TCP/UTF-8/JSON-фрагменты;
    
- различать 정상ное завершение, отмену, ошибку и обрыв без `[DONE]`;
    
- проверять идентичность Manager, слота, экземпляра и модели;
    
- не выполнять скрытую повторную генерацию;
    
- сохранять завершённый ответ и обычную историю чата;
    
- сохранить совместимость с непотоковым режимом.
    

Потоковый режим сделать основным доступным способом отображения при поддержке его движком, не уничтожая существующий обычный режим.

### 4.3. Рассуждения модели

Исследовать фактический поток установленной версии Colibri и поддерживаемые параметры.

В текущем SOURCE имеются отключения thinking, включая `enable_thinking=False` и `--no-think`. Установить, где это необходимо движку, а где является искусственным ограничением.

Требования:

- если движок предоставляет `reasoning_content` или другой документированный отдельный тип событий, передавать его без потери;
    
- показывать рассуждения отдельно от финального ответа;
    
- дать пользователю управление отображением, а режимом thinking — если его поддерживает модель;
    
- сохранять порядок событий;
    
- не смешивать reasoning с текстом ответа;
    
- не имитировать рассуждения, которых провайдер не предоставил;
    
- не обещать reasoning для модели без такой возможности.
    

Не менять настройки действующей Colibri1 ради экспериментов без OWNER GO.

### 4.4. Лимиты контекста и генерации

Проверить все числовые ограничения, способные влиять на качество и скорость: `max_tokens=512`, `--ngen 256`, `--ctx 2048`, ограничение числа сообщений и символов истории, таймауты и буферизацию.

Нельзя оставлять скрытые произвольные продуктовые ограничения, мешающие пользователю использовать возможности конкретной LLM.

При этом **не отключать защиту транспорта, ОС и сервера**. Вместо этого разделить:

- реальные пределы модели/движка/API;
    
- настраиваемые пользовательские параметры;
    
- необходимые ограничения безопасности и памяти.
    

Если часть контекста сокращается, это должно быть наблюдаемым и объяснимым поведением. Нельзя подменять реальный размер контекста произвольным числом без явной политики.

### 4.5. Измерение скорости

Внедрить диагностические измерения без записи приватного текста или секретов в логи.

Измерять минимум:

- время поступления запроса в Manager;
    
- начало запроса в Colibri;
    
- первый реальный фрагмент Colibri;
    
- первый переданный фрагмент Manager;
    
- первый полученный фрагмент Client;
    
- первое отображение браузером;
    
- завершение генерации;
    
- общую длительность;
    
- количество токенов и скорость токенов, **только если сведения предоставляет модель**.
    

Сравнивать непосредственный Colibri и Client на идентичных настройках: одна модель, один prompt, одинаковая история, thinking, состояние прогрева, параметры генерации.

**Критерий P0:** первый фрагмент виден до завершения upstream-генерации; на реальном испытании после OWNER GO получены воспроизводимые метрики и объяснена или устранена добавочная задержка.

Mock-измерения не выдавать за показатели настоящей LLM.

## 5. P1 — каталог, слоты и несколько одинаковых LLM

После прохождения офлайн-контрольной точки P0 выполнить P1 в рамках этой же TASK.

### 5.1. Интерфейс

В каждой карточке Manager предусмотреть две логические области.

**Верхняя:** список доступных моделей, обнаруженных через существующий доверенный каталог и проверенную локальную инвентаризацию. Разделять «файлы обнаружены», «движок совместим», «готова к запуску» и «уже работает».

**Нижняя:** рабочие слоты.

- Для текущего Manager первоначально отображать три сконфигурированных слота.
    
- Кнопка «+ Добавить слот» создаёт новый управляемый слот.
    
- Для каждого слота выбирается доступная модель.
    
- Внутри слота располагаются START CPU, START CUDA, STOP и фактическое состояние.
    
- Отображать привязанный экземпляр, его режим, выбранную LLM и причину недоступности операции.
    
- Не вводить глобальную константу «максимум 3».
    
- Слоты и выбор должны сохраняться при предусмотренном перезапуске Manager/Client.
    
- Оформление будущих расширенных описаний LLM — не приоритет этой TASK.
    

Добавление слота в интерфейсе должно соответствовать настоящему безопасному серверному контракту, а не только новой строке DOM.

### 5.2. Повторные экземпляры одинаковых моделей

Удалить архитектурный запрет запуска второго экземпляра по совпадению `model_key`, включая текущую проверку `model_already_managed`.

Вместо уникальности модели гарантировать уникальность `instance_id`, слота, порта, управляющих объектов и рабочих данных.

Допустить:

- Qwen3.6 CPU и Qwen3.6 CUDA одновременно;
    
- два экземпляра одной модели в CPU;
    
- два или более CUDA-экземпляра одной либо разных моделей, если установленный runtime и физические ресурсы позволяют.
    

Не обещать, что несколько CUDA дадут ускорение, или что веса обязательно будут совместно размещены в VRAM.

Сохранить общий read-only доступ к весам, но изолировать runtime, состояние, логи, временные файлы, mutex и Windows Job Object каждого экземпляра.

SQLite должен атомарно резервировать **экземпляр и конкретный слот**, а не единственное использование имени модели.

### 5.3. Ресурсы без искусственных запретов

Исторические параметры FIRST_CPU_14G (фиксированный Job cap 14 ГиБ, admission 24 ГиБ, watchdog 10 ГиБ) не должны действовать как универсальная политика для всех будущих моделей.

Переработать их в явные настройки и политику предупреждений с учётом типа модели и реальных возможностей Colibri.

**Порог 10 ГиБ свободной RAM по умолчанию — предупреждение, а не автоматический запрет.** Владелец может изменить порог и осознанно подтвердить рискованный запуск.

Показывать ожидаемый остаток RAM/VRAM, степень достоверности оценки и возможное влияние на другие модели и Valheim.

При этом не разрешать обход настоящей несовместимости runtime/CUDA, недоступных портов, системных запретов ОС, отсутствия прав или проверок принадлежности процессов.

Не отключать защиту от случайного завершения Colibri1 и чужих процессов.

### 5.4. Динамическое создание слота

Сервер должен выдавать безопасный новый `slot_id`, подходящий порт, уникальные пути и сохранённую конфигурацию.

Проверять IPv4 и IPv6, гонки, чужие слушатели, повторное использование порта, восстановление после ошибок и безопасный STOP.

Нельзя удалять работающий экземпляр посредством удаления строки интерфейса.

Защищённый существующий slot1/Colibri1 остаётся отдельным legacy-экземпляром до доказанного перехода под управление Manager. Не присваивать ему автоматически права на STOP.

## 6. Безопасность и разрешения

Сохранить действующую схему:

`Client → HTTPS Manager → локальный Colibri`

Только Manager управляет процессами. Client не получает удалённый shell.

START/STOP требуют действующего `control_models`, разрешённых слотов, проверки владельца, idempotency, атомарного журнала и явного серверного допуска.

**На этом этапе разрешены анализ и офлайн-разработка. Без отдельного OWNER GO запрещены:**

## 4. Отчёт исполнителя — минимальная форма

```text
TASK ID:
RESULT: RESULT READY / PARTIAL / BLOCKED / DRAFT
DONE: что фактически получилось
CHANGED: точные изменённые файлы
DIFF: краткая суть изменений / адрес diff
TESTS: PASS / FAIL / SKIP / NOT RUN + evidence
PROBLEMS: ошибки, ограничения и неподтверждённое
QUESTIONS: блокирующие вопросы, если остались
DOC IMPACT: что требуется обновить в документации
REPORT: постоянный проверяемый путь
NEXT: предложение, не новая назначенная TASK
```

**Правило передачи между чатами:** живое состояние и подтверждённые NEXT сохраняет ChatGPT в `13_Тактический_контекст.md` после каждого результата или значимого решения; переписка и память исполнителя не являются постоянным архивом.
