## 1. Рабочие правила Codex

1. **Источник работы:** только БЛОК 1 с задачей, назначенной владельцем, либо его прямое адресное поручение с указанными границами. План, NEXT, сообщение «можно будет» или отсутствие задач — не назначение. Поправки после назначения фиксировать как AMENDMENT с датой, не заменяя первоначальный текст.
2. **Вход:** изучить этот раздел, БЛОК 1, разрешённые источники из read matrix постановки, нужные узкие фрагменты `00_Старт.md`, `02_Назначение_проекта.md`, `03_Архитектура.md` и `13_Тактический_контекст.md` **только когда это прямо предусмотрено scope**. Не читать автоматически чужие карточки, общие архивы или весь реестр. Если источник недоступен — сообщить `SOURCE UNAVAILABLE`.
3. **Границы:** выполнять только перечисленные read/write/test-действия. Без отдельного разрешения не трогать Git/GitHub, системные настройки, работающие процессы/загрузки, модели и веса, сеть, чужие файлы и рабочее хранилище. Техническая доступность не означает разрешения. Особое согласование требуется для остановки загрузок и любых установок/удалений.
4. **Инженерный подход:** сначала установить существующее состояние, проверить переиспользование и соседние ограничения; выбрать минимальное достаточное решение. Делать проверяемые изменения, фиксировать подтверждённые факты и отдельно гипотезы. Не расширять TASK из-за попутной находки.
5. **Проверки:** выполнять оговорённые тесты в разрешённой среде, указывать команды/результаты и `PASS / FAIL / SKIP / NOT RUN`; для документации проверять содержимое, ссылки, отсутствие потерянных записей и граф Obsidian. Самопроверка Codex — доказательство исполнителя, **не** независимая приёмка.
6. **Сдача:** сохранить полный отчёт и, когда согласовано, manifest/evidence в постоянном разрешённом месте. Ответ в чате содержит `DONE / CHANGED / DIFF / PROBLEMS / QUESTIONS`, фактический статус, тесты, риски, DOC IMPACT, адрес отчёта и предложенный NEXT. Не выдавать черновик за завершённый отчёт.
7. **Приёмка и история:** ChatGPT-координатор отдельно проверяет результат, сохраняет полную исходную постановку и отчёты, заполняет персональную историю, общий реестр/хронологию и тактический контекст. Codex **не пишет себе independent PASS** и не изменяет личный архив.
8. **Сохранность:** после сдачи БЛОК 1 не очищать и не заменять, пока координатор не подтвердил архив, все AMENDMENT и повторное чтение. БЛОК 1.1 пока **ручной защищённый резерв координатора**, автоматической ротации и скрипта нет. БЛОК 4 — только для независимой оценки координатора.

### Среда Codex/Desktop — обязательная проверка путей

Codex работает **на компьютере владельца**, поэтому обращается к файлам Ultra LLM по сетевому корню `\\192.168.0.77\Server\Ultra_LLM` (например, к `Documents`, `Colibri`, `Base_LLM\Models`). Путь `C:\Server\Ultra_LLM` — локальный **на сервере**, не предполагаемый диск Codex. Он допустим внутри BAT, который будет исполняться на сервере, но файл BAT агент редактирует через UNC. Запуск BAT с UNC на компьютере агента не запускает его на сервере. Указать фактическую машину, путь, доступ, права, место выполнения и тестовый scope; если нет права удалённого запуска — `NOT RUN`. Правило — `000_Задачи для агента.md` → §3.1.

- **TASK ID / дата / исполнитель / цель и критерий результата.**

## 1. Главная цель

Превратить существующий Ultra LLM Client и Manager из системы просмотра ресурсов и общения с уже работающей моделью в полноценную управляемую систему локальных LLM.

Пользователь должен иметь возможность:

1. Видеть установленные и доступные модели каждого подключённого Manager.
    
2. Запускать выбранную модель кнопкой **«Старт CPU»** или **«Старт CUDA»**.
    
3. Останавливать собственный управляемый экземпляр кнопкой **«Стоп»**.
    
4. Автоматически получать подходящий свободный слот без ручного выбора номера.
    
5. Общаться с любой готовой разрешённой моделью в отдельном чате.
    
6. Видеть ответ постепенно, по мере генерации, как в интерфейсе Colibri.
    
7. Использовать несколько моделей одновременно при достаточных ресурсах сервера.
    

**Ожидаемый практический результат:** возможность работать с Qwen3.6 и KAT-Coder V2.5 через один Ultra LLM Client, не переключая модели вручную в Colibri.

Работоспособность KAT-Coder должна подтверждаться реальным API-ответом после отдельного согласования live-запуска, а не только наличием файлов.

## 3. Архитектурные правила

**Manager — единственный владелец управления моделями и ресурсами своего сервера.**

Client не запускает LLM самостоятельно, не выполняет удалённые команды ОС и не обращается напрямую к Colibri через LAN.

Схема:

`Web UI → локальный Client API → защищённый HTTPS Manager → локальный Colibri API`

Все существенные вычисления выполняются на сервере.

Количество Manager, моделей и слотов не ограничивать константой 3. Количество определяется реальной конфигурацией Manager и ресурсами.

Не путать слот Manager, экземпляр движка, модель и независимый разговор.

Текущая конфигурация:

- **slot1 / порт 8000:** работающая Qwen3.6 — защищённый существующий экземпляр.
    
- **slot2 / порт 8001:** подготовленный второй экземпляр, первый целевой CPU-запуск.
    
- **slot3 / порт 8002:** подготовленное место для будущего запуска, включая CUDA при наличии ресурсов.
    

Эти значения — текущая конфигурация, а не архитектурное ограничение.

## 5. Этап B — настоящее серверное управление моделями

Реализовать авторизованный контракт операций:

- Получение каталога доступных моделей и поддерживаемых режимов.
    
- Проверка возможности запуска.
    
- START CPU.
    
- START CUDA.
    
- STOP конкретного управляемого экземпляра.
    
- Получение фактического состояния операции, включая STARTING, READY, STOPPING, STOPPED, ERROR.
    
- Возврат понятной причины отказа.
    

Manager должен автоматически подбирать подходящий свободный слот.

В запросе Client указывает выбранную модель и режим исполнения, а не произвольный исполняемый файл, системную команду или порт.

Не использовать имена моделей как единственный идентификатор процесса. Предусмотреть стабильную идентичность экземпляра.

### CPU / CUDA

При выборе режима Manager проверяет реальную совместимость установленного движка и модели.

При CUDA учитывать доступность runtime, физическую VRAM, её использование и требования выбранной модели.

**Не вводить искусственное правило «12 ГБ — одна CUDA, 16 ГБ — две».** Одновременное размещение определяется фактическими затратами конкретных моделей и ресурсной политикой.

При нехватке ресурсов или отсутствии достоверных сведений — понятный отказ, без скрытого принудительного запуска.

CPU и CUDA — два отдельных пользовательских режима. Если режим недоступен, интерфейс показывает причину.

### Защита процессов

Обязательно:

- Атомарная проверка и резервирование слота.
    
- Защита от двух одновременных START.
    
- Проверка портов и реально работающих процессов.
    
- Учёт владельца и идентичности процесса.
    
- Защита от повторного использования PID.
    
- Безопасное завершение только своего экземпляра.
    
- Корректная реакция на сбой запуска или таймаут.
    
- Состояние после аварийного завершения Manager.
    
- Отсутствие автоматического удаления чужого процесса при восстановлении.
    

**Colibri1/Qwen3.6 нельзя останавливать как чужой или legacy-процесс.** Если Manager не создавал экземпляр и не может доказать право владения им, кнопка STOP недоступна.

Не менять настройки Valheim, Ollama и других запущенных пользовательских служб.

## 6. Этап C — полномочия и API

Развить существующий защищённый HTTPS Manager.

Управление жизненным циклом моделей должно требовать отдельного серверного разрешения, например `control_models`.

Не приравнивать право общения с моделью к праву её запуска и остановки. Не использовать `pairing_admin` как автоматическое разрешение управления моделями.

По умолчанию новые управляющие действия запрещены, пока владелец явно не предоставил клиенту необходимое право.

Сохранить существующие ограничения TLS, bearer-авторизации, доступных слотов, IP и локального профиля.

Для запросов START/STOP предусмотреть проверку параметров, ограничение размера, корректные коды ошибок и защиту от повторов и гонок.

Запрещено предоставлять клиенту произвольный удалённый shell или пути исполняемых программ.

Секретные токены не передавать в JS, HTML, URL или технические журналы.

Существующий чат и pairing должны продолжать работать без выдачи новых прав.

## 8. Этап E — KAT-Coder V2.5

Подготовить запуск уже имеющейся модели KAT-Coder V2.5.

Сначала проверить:

- Фактическое расположение и целостность файлов.
    
- Поддерживаемый формат и runtime.
    
- Наличие поддерживаемого CPU-режима.
    
- Возможность CUDA, если runtime действительно поддерживает её.
    
- Минимально достаточные ресурсы и ограничения.
    
- Независимость от работающей Colibri1.
    

Не считать обнаружение модели в каталоге подтверждением возможности запуска.

**Первое целевое испытание — KAT-Coder на CPU через Colibri2.**

Подготовить точную команду и план отката для исполнения на реальном сервере, затем остановиться на контрольной точке `OWNER GO REQUIRED`.

После отдельного подтверждения владельца допустимы контролируемый START, проверка `/health`, получение списка моделей, короткий реальный inference, STOP и повторный START.

При достаточных ресурсах проверить одновременный ответ Qwen3.6 и KAT-Coder через разные чаты.

Если KAT-Coder требует несовместимый runtime или превышает ресурсный бюджет, честно указать блокер и подготовить следующий вариант без самостоятельной установки новых движков или загрузки весов.

## 9. Этап F — потоковая передача ответов

Сейчас Chat API возвращает готовый ответ целиком. Требуется добавить настоящий streaming по всей цепочке:

`Colibri → Manager → Client → браузер`

Если upstream поддерживает поток, фрагменты должны отображаться по мере получения.

Сохранить возможность обычного режима «запрос → полный ответ».

Требования:

- Настоящие фрагменты от модели, а не искусственное посимвольное воспроизведение готового текста.
    
- Первый фрагмент передаётся без ожидания полного ответа.
    
- Совместимость с существующими чатами и историей.
    
- Независимое состояние переписок для разных Manager/моделей.
    
- Корректная обработка разрыва соединения, таймаута и отмены.
    
- Отсутствие дублирования сообщений в SQLite после ошибки или повтора.
    
- Ограничение размера и времени выполнения запроса.
    
- Отображение ошибок, а не бесконечный индикатор ожидания.
    

По возможности добавить измерения:

- Время до первого фрагмента.
    
- Полное время генерации.
    
- Время прохождения через Manager.
    
- Число выходных токенов и скорость, **только если значения реально измерены или возвращены провайдером**.
    

Проверить разницу между коротким запросом с чистой историей и с накопленным контекстом.

Режим отображения рассуждений делать только при наличии отдельного поддерживаемого потока от модели. Не имитировать мысли модели и не смешивать их с обычным ответом.
