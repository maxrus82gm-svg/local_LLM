## 2. Реализовать полный сценарий управления LLM

Пользователь должен иметь возможность выполнить последовательность:

**Manager → каталог моделей → выбор модели → выбор слота → CPU/CUDA → Start → READY → назначение модели чату → переписка → Stop.**

Требования:

1. Показывать актуальный каталог установленных моделей, подтверждённый Manager. Не отображать произвольные файлы как готовые к запуску модели.
2. Показывать три начальных слота и кнопку добавления новых слотов, если Manager это разрешает.
3. Позволить выбрать модель и CPU/CUDA для каждого слота.
4. Отображать состояние модели: не запущена, запускается, готова, занята, останавливается, ошибка.
5. Корректно реализовать Start и Stop через существующий авторизованный API Manager.
6. После запуска модель становится доступной для назначения любому независимому чату.
7. При остановке модели история чатов остаётся доступной.
8. Несколько экземпляров одной модели либо разные модели не должны мешать друг другу.
9. При нехватке предполагаемой RAM/VRAM показывать предупреждения и реальные причины ограничений; не обходить обязательные защитные проверки Manager.
10. При отсутствии прав показывать понятную причину и способ штатного предоставления разрешения владельцем, без скрытого обхода авторизации.

Приоритет — **полностью рабочее управление**, а не косметическое обновление интерфейса.

## 4. P1 — полноценные независимые чаты

Перестроить структуру хранения и UI так, чтобы чат был отдельной постоянной сущностью с собственным уникальным `chat_id`, названием, временем создания и историей.

**Обязательные функции:**

- **Новый чат:** отдельный пустой диалог, даже если та же модель и тот же слот уже используются другим чатом.
    
- Несколько независимых чатов с одной моделью.
    
- Список чатов, переключение, переименование, сохранение после F5 и перезапуска Client.
    
- Выбор доступного Manager/слота/модели **для конкретного чата**, с возможностью смены назначения без утраты его истории.
    
- Остановка модели либо её временная недоступность не должна удалять чат или делать историю недоступной.
    
- При смене модели история остаётся, но учитывать несовместимости форматов и предупреждать, если контекст не может быть передан.
    
- История чатов хранится в Client; Manager не становится главным хранилищем переписки.
    
- Прежнюю базу текущего Client мигрировать без потерь в понятную legacy-структуру. Сначала backup и тест миграции на копии.
    
- Не связывать идентичность чата с PID, портом или жизненным циклом процесса модели.
    

**Отдельные операции:**

1. **Новый чат** — независимый новый контекст.
    
2. **Сбросить контекст** — сохранить историю для просмотра, но не посылать старые реплики в следующих запросах этого чата, пока контекст не будет вновь явно выбран/переустановлен.
    
3. **Очистить переписку** — убрать историю только выбранного чата после явного подтверждения. Сформулировать последствия; предусмотреть безопасный backup/восстановление в разумных пределах.
    
4. **Удалить чат** — удалить саму сущность после отдельного подтверждения.
    

Не путать «очистить переписку», «сбросить контекст», «остановить модель» и «удалить слот». Эти операции имеют разные последствия.

**Режим** `**max_messages=0**` **сохранить без изменений смысла:** отправляется только текущий пользовательский запрос, история в базе не стирается. Настройка действует для соответствующего чата.

При планировании учесть существующую возможность нескольких Manager, слотов и параллельных потоков, не сломать её.

## 5. P1 — поток, `busy` и восстановление отправки

Исправить наблюдённую нестабильность:

- Во время активной генерации `slot1` закономерно может иметь `availability=busy`. Это не означает отключённую модель.
    
- Если текущий чат владеет активным запросом, показывать **«Модель отвечает»**, а не ложное **«Слот недоступен»**.
    
- По завершении потока, получении `done`, ошибке или отмене корректно освобождать локальное состояние запроса.
    
- После завершения получать актуальный статус Manager; не держать устаревший снимок до фонового опроса раз в 25 секунд.
    
- Учитывать реальный период освобождения scheduler: если слот ещё занят, отображать это корректно, без ложной активации кнопки.
    
- Использовать ограниченные повторные проверки с backoff, без постоянного опроса и искусственных пауз.
    
- Сохранить защиту от двойного Enter, IME, повторной отправки и request ID.
    
- Проверить сценарии одновременных чатов, отмены, смены слота, переключения чатов и F5.
    
- Проверить, что `Stop` одной LLM не влияет на другую и не уничтожает чаты.
    
- Разделить отображаемые состояния: `READY`, `BUSY`, `NOT RUNNING`, `DENIED`, `UNKNOWN`, `GENERATING`, `CANCELLING`, `ERROR`.
    
- Запуск модели по-прежнему требует реальных разрешений Manager. Не обходить `control_models=false` и не изображать остановленную модель готовой.
    

Снять измерения между `done`, освобождением slot scheduler, получением свежего snapshot и фактическим восстановлением ввода.

## 4. Отчёт исполнителя — минимальная форма

```text
TASK ID:
RESULT: RESULT READY / PARTIAL / BLOCKED / DRAFT
DONE: что фактически получилось
CHANGED: точные изменённые файлы
DIFF: краткая суть изменений / адрес diff
TESTS: PASS / FAIL / SKIP / NOT RUN + evidence
PROBLEMS: ошибки, ограничения и неподтверждённое
QUESTIONS: блокирующие вопросы, если остались
DOC IMPACT: что требуется обновить в документации
REPORT: постоянный проверяемый путь
NEXT: предложение, не новая назначенная TASK
```

**Правило передачи между чатами:** живое состояние и подтверждённые NEXT сохраняет ChatGPT в `13_Тактический_контекст.md` после каждого результата или значимого решения; переписка и память исполнителя не являются постоянным архивом.
