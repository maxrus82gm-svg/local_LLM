## Qwen3.8-Flash-Next — вариант для самостоятельного исследования

**Почему интересна:** большая MoE с ~6B активных параметров на шаг; Colibrì умеет хранить экспертов на SSD и кешировать ограниченную часть в RAM/VRAM. Это **не гарантия быстрого ответа**: пропускная способность SSD, RAM, backend, кэш экспертов и контекст критичны.

**Проверенные форматы из Unsloth (размер всех частей файла, десятичные GB):**

| GGUF вариант | Размер всего набора | Компромисс |
| --- | ---: | --- |
| `UD-IQ1_S` | ~72,5 GB | Минимальный объём, максимальный риск потери точности |
| `UD-IQ1_M` | ~74,5 GB | Чуть больше, 1-битный класс |
| `UD-Q2_K_XL` | ~78,9 GB | Потенциально разумный тест качества против 1-bit; не обещает ускорение |
| `UD-IQ3_XXS` | ~82,0 GB | Более высокий битовый бюджет при больших расходах на диск |
| `UD-Q3_K_XL` | ~90,0 GB | Более точный и тяжёлый |
| `UD-IQ4_XS` | ~93,7 GB | Отдельная 4-битная смесь; всё ещё значительно больше RAM |

Источник: https://huggingface.co/unsloth/Qwen3.8-Flash-Next-GGUF . **Большие GGUF разбиты на несколько shard-файлов**: нужны все части одного выбранного квантования в одной папке. Это размеры на диске, НЕ требования к RAM; при 48 GB RAM возможен disk-streaming в Colibrì, но без гарантий скорости и без проверки конкретного GGUF.

### Вариант A — Colibrì + опубликованный GGUF (первым изучать именно его)

**Документально поддерживается:** `general.architecture=qwen4exp` → `qwen38`; `coli import` считывает GGUF без дополнительной квантовки и по умолчанию работает в режиме `--mode link` (исходные веса остаются там, где лежат). Для `qwen4exp` копирование формата не поддерживается; использовать link.

Порядок **только после отдельного USER GO, без выполнения сейчас**:

1. Скачать полный набор shard-файлов выбранной версии в отдельную папку **на SSD сервера**, не поверх KAT/Qwen.
2. Проверить число частей, размеры, контрольные суммы, свободный SSD, RAM и работу текущего Colibrì; сохранить снимок конфигурации/работающих процессов. **Не скачивать два разных квантования без необходимости.**
3. На **самом сервере** в папке существующей установки Colibrì применить подходящий launcher. Ориентир по Windows-документации: в исходном дереве `py -3 c\coli`, а в release-архиве — `coli.cmd`. Не считать `coli.cmd` существующим в текущей исходной папке без проверки.
4. **Иллюстрация CLI**, пути уточнить по фактической папке после согласования:

```powershell
# Выполнять только на сервере после явного разрешения, НЕ сейчас:
# cd C:\Server\Ultra_LLM\Colibri
# py -3 c\coli import "C:\Server\Ultra_LLM\Base_LLM\Models\FlashNext\Qwen3.8-Flash-Next-UD-Q2_K_XL-00001-of-00003.gguf"
# py -3 c\coli doctor --model "<папка, созданная import>"
# py -3 c\coli plan --model "<папка, созданная import>" --ram 40 --ctx 8192
# py -3 c\coli chat --model "<папка, созданная import>"
```

**Важно:** указанное имя первого shard — пример по схеме Unsloth, проверить по полученным файлам; аргументы `--ram`/контекст — пример для планирования, а не подтверждённая пригодная конфигурация. Не запускать вторую активную Colibrì с портом 8000 одновременно; проверить план и остановить существующую модель **только по решению владельца**. Начинать с ограниченного контекста, фиксировать TTFT, скорость, RAM/VRAM, SSD I/O и ошибки.

Документы: https://github.com/JustVugg/colibri/blob/main/docs/gguf.md ; https://github.com/JustVugg/colibri/blob/main/docs/windows.md ; https://github.com/JustVugg/colibri/blob/main/docs/qwen38.md

### Вариант B — Colibrì + официальный FP8 Safetensors с потоковой загрузкой экспертов

- Официальный чекпойнт `Qwen/Qwen3.8-Flash-Next-FP8`: около 185,5 GB на SSD.
- `qwen38.c` описывает запуск напрямую из sharded Safetensors, с постоянным набором dense-весов в RAM и выборочным кэшем экспертов. По отчёту авторов это возможно при RAM существенно меньше размера весов, но скорость зависит от SSD и кэша.
- Опциональный sidecar с экспертами `int4-g64` занимает около **68 GB дополнительно к исходным FP8 shards**, а НЕ вместо их скачивания; нельзя описывать «68 GB» как самостоятельный полный FP8-пакет.
- Документация: https://github.com/JustVugg/colibri/blob/main/docs/qwen38.md ; checkpoint https://huggingface.co/Qwen/Qwen3.8-Flash-Next-FP8
- Для нашего сценария это **запасной исследовательский маршрут** из-за потребления SSD, сложности подготовки и неизвестной скорости на RTX 3070/48 GB RAM.

### Вариант C — Ollama / иной GGUF runtime (сравнительный, НЕ доказан)

- Альтернатива для сравнения качества/скорости на тех же GGUF; движок сам по себе не обеспечивает экспертный streaming Colibrì и не обещает нормальную работу набора ~79GB на 48GB RAM. Возможны memory-mapping, paging и очень долгая генерация.
- Ссылка: https://ollama.com/download/windows ; документация локального `Modelfile`: https://docs.ollama.com/modelfile
- **Статус:** Ollama installation / Flash-Next launch = NOT VERIFIED. Не выполнять импорт, создание новой модели и настройку службы без согласования.

### Оценка и следующий шаг для Flash-Next

**Категория:** `ПРЕТЕНДЕНТ / RESEARCH / NOT DOWNLOADED / NOT RUN`, а не «неподходящая» без теста. Для сравнительного программирования нужен одинаковый МАЯК-47, отдельно пользовательская проверка русского, tool calling, скорость и соответствие C++/UE5. Предварительная гипотеза: Colibrì GGUF `UD-Q2_K_XL` имеет смысл оценить первым из Flash-Next, если хватает диска и владельцу подходит качество низкого квантования; **никакой загрузки сейчас не назначено**.

## Универсальные правила безопасного подключения

- Разделять **скачано**, **на серверном SSD**, **импортировано**, **сервис READY**, **отвечает**, **прошло тест** — отдельные статусы.
- Документировать точный идентификатор файла и квантования, версию Colibrì/движка, backend (CPU/Vulkan/CUDA), RAM/VRAM, свободный SSD, контекст и API-порт.
- Отдельно сохранять неизменяемые оригиналы ответов и логи в `Reports/`; перед переключением модели проверить незаконченный R4 у KAT.
- Команды выше — **примеры/план**, они не выполнялись и не дают разрешения на изменение окружения.
