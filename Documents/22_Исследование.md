# 22 — Исследование

Накопительный журнал исследований Colibri Ultra. Новые вопросы добавляются последовательно: «Исследование №2», «Исследование №3» и т. д. Для каждой темы фиксируем цель, известные факты, гипотезы, способ проверки, результат и решение владельца. Исследование не означает автоматического запуска работ или изменения production.

## Исследование №1 — Динамическое распределение VRAM из Client

**Дата:** 22.11.2026
**ID:** RES-UL-DYNAMIC-VRAM-20261122-001
**Статус:** OPEN / исследование возможностей, реализация NOT RUN.

### Цель

Менять бюджет размещения весов MoE непосредственно из Ultra LLM Client во время генерации, без остановки модели, потери контекста, истории или текущего ответа. Наблюдать изменение текущей и средней скорости генерации, находить эффективное распределение RAM/VRAM для каждой модели и GPU.

### Что известно и что необходимо выяснить

- Текущий профиль Colibri задаёт `--vram`, `COLI_CUDA_CHAIN`, `COLI_CUDA_CHAIN_ROWS` при запуске. Save не меняет активный экземпляр; новый бюджет применяется после явного Stop/Start. Порог VRAM — предупреждение, не аппаратный лимит.
- В MoE Router выбирает экспертов для токенов; физическое размещение их весов — ответственность движка. Не все эксперты вне VRAM обязательно копируются на GPU: возможны вычисления на CPU.
- В upstream Colibri описана динамическая замена резидентных экспертов и CUDA host pool. Это не доказывает возможность менять ёмкость кэша без перезапуска в установленной сборке. Проверить её точную версию, исходники, жизненный цикл allocator/tier, безопасные точки смены лимита, наличие API.
- Уточнить реальное размещение KV, рабочие буферы CUDA Chain и staging; возможность увеличить/уменьшить бюджет без OOM, повреждения KV или потери ответа. SSD I/O во время генерации пока не доказан.
- Исследовать общий бюджет, доступный движку: например, веса 5 ГиБ + до 2 ГиБ KV/буферов на GPU 8 ГиБ, с резервом под систему. Это желаемая политика, а не гарантированная возможность текущего Colibri.

### Предлагаемая схема и телеметрия

Client → авторизованный Manager → адаптер/поддерживаемый API Colibri. Client задаёт запрос на изменение, Manager проверяет права, instance_id, свободную память, применимость и результат. Отдельно показывать желаемый и фактический бюджеты, статус применения, причину отказа; неподдерживаемые поля = «Нет данных». Не имитировать изменение записи в SQLite как изменение реальной VRAM.

| Показатель | Назначение |
| --- | --- |
| Текущая/средняя т/с, prefill | Эффект изменения бюджета |
| VRAM/RAM, KV, рабочие буферы | Фактические ресурсы, запас |
| GPU expert cache hit/miss | Попадания и перемещения экспертов |
| PCIe RX/TX, SSD read | Выявление узких мест |
| OOM, fallback, PID, instance_id | Стабильность и отсутствие перезапуска |

### План проверки

1. Изучить исходники установленной версии и существующие механизмы динамического размещения; установить, есть ли безопасный runtime setter бюджета.
2. Если setter отсутствует, оценить минимальную доработку движка и контракт API; не ограничиваться ползунком UI. При необходимости предложить отдельную задачу на адаптер/патч.
3. Офлайн проверить владение памятью, синхронизацию с in-flight CUDA kernels, увеличение/уменьшение ёмкости, конкурентные запросы, отказ при недостатке памяти, rollback. Жёсткий предел возможен только при подтверждённой поддержке allocator/движка; наблюдение WDDM само по себе не предотвращает OOM.
4. После отдельного OWNER GO — изолированный live A/B: одинаковая модель/контекст/промпт, изменить бюджет 3.5 → 5 → 3.5 ГиБ на ходу, Chain OFF в первом опыте; далее Chain ON отдельно. Сохранить PID/instance_id, непрерывность SSE, KV/историю, замеры до/после и контроль качества. Проверить, что бюджет действительно сменился и запрос не потерян.

**Источники:** [Colibri — ENVIRONMENT](https://github.com/JustVugg/colibri/blob/0a5504a1dc64f86fcd0fe7db298b0448c730e7e6/docs/ENVIRONMENT.md), [CUDA tier](https://github.com/JustVugg/colibri/blob/0a5504a1dc64f86fcd0fe7db298b0448c730e7e6/docs/qwen36-cuda-tier.md), [CUDA chain](https://github.com/JustVugg/colibri/blob/0a5504a1dc64f86fcd0fe7db298b0448c730e7e6/c/qwen36_cuda_chain.h); внутренние №03/18 и KAT-профили №17/17.1.

**Границы:** пока только журнал исследования. Не менять код, модели, рабочий Manager/Client, текущий запрос. Будущую реализацию согласовать отдельно. Результат и выводы дописывать сюда по мере проверки.



## Исследование №2 — Влияние глобального промпта на качество LLM

**Дата:** 22.11.2026
**Статус:** OPEN / эксперимент предложен владельцем, результат ещё не получен.

Проверить, улучшает ли короткий универсальный протокол самопроверки качество программирования: соблюдение требований, синтаксис и типы, согласованность компонентов, граничные сценарии и честность заявлений о тестировании. Повторить задачу «Сапёр» на Qwen3.6 в новом чате с тем же исходным заданием, без подсказок о прежних ошибках; отдельно измерить скорость и качество. Первый предложенный пользователем прогон одновременно меняет глобальный промпт и бюджет весов на 5 ГиБ — практический комбинированный опыт, не чистый A/B. Для выделения влияния промпта нужен отдельный парный тест с неизменным профилем. Не считать результат подтверждённым до независимой проверки.

## Исследование №3 — Уточнение запроса на ходу (Live Steering)

**Дата:** 22.11.2026
**ID:** RES-UL-LIVE-STEERING-20261122-003
**Статус:** OPEN / исследование возможностей; реализация NOT RUN.

### Цель

Во время генерации пользователь или внешний агент может отправить уточнение, дополнительное требование или обновлённые глобальные инструкции. Модель должна учесть его и продолжить решение без перезапуска экземпляра, с сохранением исходной задачи и полезной уже полученной части ответа. При этом остановка текущего запроса не должна означать остановку LLM.

### Текущее состояние и возможные препятствия

- Client уже загружает текущий global_prompt.json при подготовке каждого нового запроса (prepare_chat_messages). В существующем контракте Manager глобальный промпт добавляется к первому user-сообщению во временной копии, а не передаётся отдельной system-ролью. Изменение файла не меняет уже переданный запрос.
- В активной генерации новые инструкции требуют пересмотра токенов контекста/KV либо специального механизма движка. Установленный Colibri пока не подтверждён как поддерживающий настоящую вставку инструкций в тот же активный inference. Изучить API и безопасные точки прерывания, применение новых сообщений, переиспользование неизменного префикса KV; не обещать продолжение без повторного prefill.
- Практический первый вариант: сохранить полезный видимый фрагмент как незавершённый ответ, отменить текущий запрос, получить подтверждение освобождения именно этого запроса/слота, сформировать продолжение с исходной задачей, новым уточнением, актуальным глобальным промптом и необходимой частичной историей; отправить новый request_id в тот же instance_id. Не пересылать сырой reasoning как обычный ответ по умолчанию. Фактическое возобновление с того же места не гарантируется.
- Существующий Client сохраняет exchange при успешном done; при cancel/error частичный ответ не гарантированно сохраняется. Сначала решить эту OPEN проблему. Проверить задержку отмены, гонки cancel/done, устаревшие SSE-фрагменты, повторную отправку и отмену продолжения. Никаких автоматических рестартов, дублирования запросов или ложных подтверждений.
- Сравнить полное продолжение, перегенерацию с обновлённым требованием и (если движок поддержит) нативное midstream steering. Отдельно изучить системную роль и приоритет инструкций, а не только префикс user-сообщения.

### Архитектура с Web Alarm Ultra

Принцип владельца: Web Alarm Ultra (WUA) — владелец внешнего чата/контекста; Ultra LLM Client служит программным мостом к нескольким Manager. При внешней работе не требуется автоматически создавать или вести отдельную копию пользовательского чата в GUI Client. Собственные локальные чаты Client остаются самостоятельным режимом.

Рекомендуемый контракт (гипотеза, не утверждённая реализация):
WUA (API / MCP-инструменты) → Client Bridge API → авторизованный Manager → адаптер Colibri / другой движок.
В обратную сторону — streaming, статусы, подтверждения команд, usage/telemetry, ошибки.

Client Bridge маршрутизирует вызовы, держит краткоживущие привязки external conversation/turn, manager_id, slot_id, instance_id, request_id; не подменяет владение историей WUA. Manager отвечает за права, занятость, контроль конкретного экземпляра и взаимодействие с движком. WUA хранит пользовательскую историю, исходный запрос, уточнения и принятые частичные результаты. Отдельный журнал технических событий возможен без обязательного дублирования содержания чата.

API — основной транспорт потока/управления; MCP — набор инструментов над тем же контрактом (например, status, cancel, steer, capabilities). Не создавать второй независимый механизм управления из MCP. Имена операций условные; реальные маршруты и форматы спроектировать отдельно. Изучить capability negotiation для разных движков: native steering, cancel-and-continue, поддержка system-role, сохранение префикса, live telemetry. При отсутствии возможности — честный статус unsupported, без скрытого перезапуска. Внешние команды должны проверяться Manager по правам, исходному запросу и instance_id; повторы не должны запускать дубликаты.

Альтернативу WUA → Manager напрямую допустимо исследовать для автономных сервисов, но не вводить второй конкурирующий путь управления сейчас. Предпочтение владельца — Client Bridge как единая точка работы с несколькими Manager; вопрос границ API/MCP и владения контекстом учитывать в дальнейшей архитектуре обоих проектов.

### План исследования

1. Сверить установленную версию Colibri и реальный контракт cancel/continuation/KV/system-role.
2. Изучить существующий Client/Manager streaming и контракт внешнего моста; предложить единый протокол уточнения и сохранения частичных результатов.
3. Проверить офлайн штатную отмену и продолжение, потерю связи, повтор команды, конфликт двух клиентов, завершение до отмены, изоляцию чужого запроса.
4. После отдельного OWNER GO провести изолированный LIVE тест: дать задачу, во время генерации добавить новое требование, проверить явное подтверждение, сохранность частичного текста, выполнение уточнения, отсутствие потери истории и перезапуска экземпляра; замерить время отмены и нового prefill.
5. Повторить сценарий через внешний API/MCP-адаптер без создания дублирующего GUI-чата, проверить совместимость с будущим WUA.

**Источники текущего состояния:** Client_Ultra_LLM/web_client.py (prepare_chat_messages, _run_chat_stream), Manager_Ultra_LLM/live_manager.py; документы №03/18/13. **Границы:** только постановка исследования, не реализация. Текущие LLM, Manager, Client и Web Alarm Ultra не изменять без отдельной задачи.



## Исследование №4 — Независимая генерация на Manager и восстановление подключения Client

**Дата:** 22.11.2026
**ID:** RES-UL-DETACHED-STREAM-20261122-004
**Статус:** OPEN / исследование, реализация NOT RUN.

**Требование владельца:** закрытие Client, вкладки или потеря сети не должны отменять принятый Manager запрос. Manager продолжает inference, хранит полученные фрагменты и состояние; при повторном подключении Client показывает текущие параметры, накопленный ответ, reasoning, текущий прогресс/телеметрию и итог без повторного запуска запроса. Явный Cancel/Stop остаётся отдельной операцией. Учитывать будущую работу WUA через Client Bridge без обязательного локального GUI-чата (№3).

Предлагаемая архитектура: Manager владеет жизненным циклом задания независимо от SSE-подписчика; producer получает поток от движка, consumer только подписывается. Буфер событий на Manager с монотонным seq и привязкой manager_id/slot_id/instance_id/request_id/owner. Исследовать ограниченный RAM-буфер и дисковый spool/устойчивое хранилище, лимиты, TTL, защиту, очистку, backpressure, политику replay gap и накопленный snapshot. Не допускать незаметной потери ответа из-за отключения потребителя. При reconnect — auth, поиск своего задания, snapshot + replay после cursor, live stream без дубликатов; финал сохранять ровно один раз. Manager удерживает технический результат ограниченный срок; WUA владеет внешней историей. API и MCP используют один контракт. Различать reconnect Client и восстановление после падения Manager/движка: последнее не гарантирует продолжение inference и требует отдельного исследования.

Проверить существующие cancellation/timeout и transport ownership, идентичность запроса, повтор подписки/команды, гонку snapshot/live/done, медленного и нескольких потребителей, overflow, disconnect/Client shutdown, повторный запуск Client, явный Cancel, ошибку движка, сохранность данных и отсутствие второго inference. Офлайн тесты, затем изолированный LIVE только по OWNER GO: закрыть Client во время генерации, подтвердить продолжение на Manager, открыть Client, получить всё недостающее и итог. Не трогать текущий ночной тест; пока документация.
