2. **После каждой записи — обязательная проверка.** Прочитать изменённый файл обратно из удалённой `GPT_2_local`, проверить содержимое, новый SHA, ветку и доступность коммита в GitHub; сверить `main...GPT_2_local` и выдать владельцу номер, SHA и ссылку. Его обычный путь в GitHub Desktop: `Fetch origin` (если нужно, обновить локальную `GPT_2_local` через `Pull origin`), сделать текущей ветку `main`, затем `Branch → Merge into current branch… → GPT_2_local`, проверить результат и **самостоятельно `Push origin` для `main`**. 4. Для значимых инвариантов проверять результат независимым оракулом: байты, файлы, ответ, состояние или событие; для опасных рисков добавлять negative controls, которые на намеренной неисправности дают ожидаемый RED. Пустой тестовый набор, любой exception или просто exit 0 не означают PASS.
5. При дефекте зафиксировать воспроизведение, доказанную причину или честную гипотезу, последствия и точные границы исправления. Не ослаблять тесты ради PASS. Собственное исправление проверяющего не становится автоматически независимо принятым.

#### 5.1.2. Самостоятельные тесты и независимый CI

1. Координатор **сам инициирует** подходящие повторные и дополнительные unit/integration/API/security/negative/fault/recovery/regression/JS/Chrome/packaging-тесты по риску и применимости. Полезные проверенные тесты сохранять в поддерживаемой базе при разрешённом write-scope; не дублировать без причины.
2. Для Windows стандарт — **GitHub Actions `windows-latest`** на точном source SHA. При необходимости использовать другую целевую ОС. В workflow: конечный timeout, минимальные permissions (`contents: read`), `persist-credentials: false`, закреплённые версии, правильный dependency closure, guarded imports, изолированные synthetic данные, короткие TEMP/sparse checkout при необходимости.
3. Не передавать приватные tokens/пользовательскую историю в CI, не разрешать произвольную сеть/платные API/production-процессы только ради теста; реальные операции требуют отдельного OWNER GO. Сетевой setup зависимостей не означает сетевой допуск тестируемому приложению.
4. **Запустить** настоящий workflow разрешённым механизмом и зафиксировать run ID, SHA, среду/версии, suites, PASS/FAIL/ERROR/SKIP, stdout/stderr, exit codes, artifacts и negative controls. Написанный YAML, старый зелёный run или отчёт Codex не считаются новым независимым CI. Сохранять первоначальный FAIL и последующие NOT RUN даже после успешного повтора.
5. Если CI недоступен: `CI WINDOWS NOT RUN / BLOCKED` с точной причиной, а не обещание. GitHub-hosted Windows не тождествен рабочему EXE, физическому ПК, GPU/Colibri и настоящей сетевой среде.
6. Новые tracked тесты/workflow, коммиты и push только в рамках утверждённой задачи и разрешённой `GPT_2_local`; один итоговый коммит на задачу. `main` не менять. Для отдельной работы/прав — FOLLOWUP/адресное согласование, без обхода.

#### 5.1.3. Настоящее приложение, пользователь, UX

1. После технической готовности и разрешений проверять **настоящую установку/EXE или веб-вход**, сервер/API/режимы, реальную генерацию/первый отклик и поток, сохранение/ошибки, restart и возврат. Fake/mock PASS подтверждает лишь тестовую среду; не выдавать его за REAL APPLICATION PASS. LIVE/paid/inference/START/STOP/cutover — строго отдельные gates.
2. **Каждое значимое изменение пользовательского взаимодействия лично проверяет владелец**: интерфейс, расположение/масштаб/подписи/кнопки, выбор модели/режима, новые функции, скорость/поток, чаты/история, установка, подключение, ошибки. Показывать рабочий продукт **целиком**, а не отдельный скриншот; важны удобство, понятность и необходимость функции.
3. Координатор сам предлагает короткий OWNER smoke: точная сборка, безопасный запуск, что изменилось, **2–6 действий** с ожидаемым результатом, что оценить визуально и по ощущениям, какие риски/NOT RUN открыты, как остановить и откатить. Не просить владельца повторять автоматизируемые инженерные тесты. Не говорить «осталось только у тебя проверить», пока технические проверки не завершены.
4. **Внутренние изменения без изменения видимого поведения** (например, refactor, диагностический код, документ) допускают `USER UX NOT REQUIRED` с обоснованием после технической приёмки. Но новые/изменённые пользовательские маршруты не закрываются без реального `USER UX ACCEPTED`; до отзыва `PENDING`.
5. Для переносимости отдельно проверять другие ПК, чистую Windows, обычные права, отсутствие runtime, странные пути, AV, LAN, CPU/GPU/RAM, обновление/rollback по мере готовности. Hosted CI автоматически этого не подтверждает.
6. Замечания и идеи владельца сохранять как `BUG / USER OBSERVATION / UX-PRODUCT FOLLOWUP / NEW IDEA` с шагом, фактом и желаемым поведением. Новые идеи не расширяют уже утверждённую TASK без согласования.

#### 5.1.4. Обязательный отчёт и документный цикл

**Раздельные вердикты:** `AUTHOR TESTED`; `TECHNICAL PASS/FAIL/PARTIAL/NOT RUN`; `CI WINDOWS PASS/FAIL/NOT RUN` только с актуальным run ID; `REAL APPLICATION PASS/FAIL/NOT RUN`; `USER UX ACCEPTED/ISSUE/CHANGE REQUEST/PENDING/NOT REQUIRED`; `RELEASE READY/HOLD`. `EVIDENCE REVIEW PASS` означает чтение и анализ evidence, **не** лично запущенные тесты/CI/LIVE.

**На выходе каждой TASK:** идентификатор и SHA; инженерный review/недочёты; авторские тесты; лично повторённые и новые тесты; CI workflow/run ID или NOT RUN; negative RED vs неожиданные FAIL; настоящая программа; OWNER UX; безопасность/данные/backup/rollback; BUG/IDEA; отдельные статусы; NEXT, ответственный, необходимый GO.

**История/контекст обязательны и не отменяются:** №05 — реестр ID/OPEN/FOLLOWUP; №06 — принятые владельцем решения; №07 БЛОК 4 — независимый вердикт (БЛОК 1 пишет владелец, не ChatGPT); №09 — последовательная история и evidence с FAIL; №13 — актуальный тактический NOW/NEXT **после каждого события**; №18 — технические сведения; №00 — точка входа. Сохранять исходники TASK/AMENDMENT, отчёты, архивы. После записи сверять diff, readback, SHA, ссылки, статусы и ветку `GPT_2_local`; при недоступности честно `DOC UPDATE BLOCKED`. Не стирать историю при новом чате.

**Цепочка:** `исходники/риски → независимый инженерный review → свои и новые tests → применимый CI → настоящее приложение → USER UX по необходимости → баги и идеи → документы/история/контекст → отдельное решение о следующем gate`.
