## 1. Роли и полномочия

- **Владелец:** определяет цели и приоритеты, назначает TASK, утверждает изменения scope, разрешает рискованные действия и решает, продолжать ли этапы.

## 3.3. Обязательная нумерация Git-коммитов ChatGPT (решение владельца 07.11.2026)

- **Нумерация сквозная:** для каждого нового коммита ChatGPT в `local_LLM` начинать сообщение с порядкового номера и краткого описания, например `02 — Настроить домашнюю Colibri и документировать пути`. Принятая владельцем предыдущая работа условно имеет номер `01`; следующий коммит — **`02`**, затем `03`, `04` и далее, без пропусков, повторов и переписывания старых коммитов. Номер относится к коммитам ChatGPT, не к TASK или документам.
- **Перед каждой записью:** фактически проверить актуальные `main` и `GPT`, последний опубликованный коммит и использованные номера. При параллельных изменениях или неясном номере — остановиться и уточнить у владельца; не выбирать номер по памяти. По возможности объединять связанные изменения в один логический коммит.
- **Строго только `GPT`:** ChatGPT коммитит и отправляет в `GPT`; не коммитит, не сливает и не делает rebase/force-push в `main`. Владелец самостоятельно принимает изменения в `main`. После push проверить SHA, фактический номер и diff `main...GPT` и сообщить владельцу. Номер не считается использованным без подтверждения удалённой ветки.

## 4. Единый формат выдачи задач исполнителям

Перед постановкой проверить дубликаты, прошлые незавершённые пункты, право исполнителя читать/писать нужные файлы, отсутствие пересечений и возможные ограничения по моделям/диску/памяти. Устные планы не считать назначенными.

Для обычного нового поручения готовить **три отдельные копируемые части в чате**:

**БЛОК 1 — полная TASK для вставки владельцем в карточку исполнителя:**
- TASK ID, дата, исполнитель, цель и ожидаемый проверяемый результат.
- Read matrix: что и почему необходимо прочитать; точные файлы/разделы.
- Write/test scope, запреты, доступы, границы среды и неразрешённые действия.
- План работ, критерии приёмки, обязательные тесты, отчётный путь, evidence.
- Неизвестное/риски, требования к `DONE / CHANGED / DIFF / PROBLEMS / QUESTIONS`.
- Что **не** является частью этой TASK и где нужен следующий USER GO.

**БЛОК 2 — краткий активатор:** короткое сообщение исполнителю после того, как владелец вставил БЛОК 1; сам по себе не заменяет постановку.

**БЛОК 3 — небольшой follow-up:** что и где исполнитель должен сообщить после сдачи; без нового расширения scope.

**Только владелец назначает TASK** (вставляет её в БЛОК 1 или даёт явное адресное поручение). Промежуточные корректировки — датированные `AMENDMENT`, оригинальную TASK не переписывать.

## 5. Порядок контроля исполнения и приёмки

1. Получить финальный пакет: полный `report`, перечень изменённых файлов, по необходимости manifest/evidence, фактические команды и результаты, `PASS/FAIL/SKIP/NOT RUN`, ограничения и `DOC IMPACT`.

3. В БЛОКЕ 4 фиксировать отдельный verdict `PASS / PARTIAL / REVISE / FAIL / BLOCKED` с датой, конкретной версией, scope проверки и `NOT RUN`. `RESULT READY` означает сдачу, **не** `DONE / VERIFIED`.
4. Если результат недостаточен — документировать дефект или проверочный пробел; все незавершённые действия с владельцем и условием закрытия переносить в `05_Реестр_задач.md` → FOLLOWUP. Назначение successor само по себе не закрывает остаток.
5. Сначала сохранить и повторно прочитать полную исходную TASK, все AMENDMENT, отчёты/evidence и персональную историю. Затем обновить реестр, общую хронологию `09_История_задач.md`, личную историю, при решении владельца `06_Журнал_решений.md`. **Карточку освобождать последней** и только при доказанной сохранности.
6. Внесённые исправления собственного текста ChatGPT не объявлять независимым PASS другого участника без отдельной проверки.

## 6.2. Непрерывная актуальность документации и экономия контекста (OWNER RULE 08.11.2026)

1. После значимого результата, промежуточного server gate, независимого verdict, изменения курса или OPEN **сначала** обновить документы и проверить их взаимную согласованность, **затем** передавать новую TASK. Активную TASK не объявлять закрытой, если закрыт лишь её промежуточный этап.
2. Схема идентификаторов: `TASK-ID` — работа; `EVID-ID` — проверяемое свидетельство/замер; `FOLLOWUP-ID` — незавершённое действие; `DEC-ID` — решение владельца; `DOC-EVENT-ID` — документное изменение. У каждого ID ровно один основной адрес, краткий статус, ссылка на связанный TASK и источник. Не переиспользовать ID для новой независимой работы.
3. **Главный индекс — существующий №05** (ID → статус → точный адрес №07/09/18/06 → связанные OPEN); №13 — только последние подтверждённые факты и NEXT; №09 — развёрнутая неизменяемая история/evidence; №06 — решения; №18 — технические характеристики и шаги; №07 — действующая постановка и её независимая проверка. Новые документы и вторые полные копии не создавать без разрешения владельца.
4. Новому чату/исполнителю сначала дать **короткий пакет ID + ссылки + OPEN**, читать адресные фрагменты, а не весь архив. Удалять уникальные доказательства, точные TASK/AMENDMENT или негативные результаты ради экономии токенов запрещено; вместо этого выносить подробности в основной источник и давать адрес.
5. После правки выполнить diff/readback, сверить ID, ссылки, БЛОК 1 и несовместимые статусы; GitHub — первоисточник. Запись ChatGPT только в `GPT`; если GitHub write = 403, не выдавать локальный edit за опубликованный — подготовить в синхронизированном клоне, владелец проверяет и публикует сам.
