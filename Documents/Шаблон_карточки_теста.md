# Образец испытания локальной LLM — стандарт v1.1

**Назначение:** внутренний шаблон для ChatGPT-координатора, **не отдельный результат и не узел рабочего графа**. Использовать при создании двух документов каждой LLM: подробное техническое досье `[номер]_[LLM].md` и короткое резюме `[номер].1_[LLM]_кратко.md`. Действующая карта и правила входа — №14, оперативное состояние — №13.

**Дата начала методики:** 2026-11-01 · **Уточнение:** после независимого анализа R2 KAT-Coder; исходное тестовое задание МАЯК-47 v1.0 не изменялось.

**Ответственный и порядок:** владелец решает, когда тестировать/запускать/допускать исправления; ChatGPT готовит и анализирует документацию. Сначала получить полный исходный ответ и сохранить без правок в `Reports/`; затем проверить код независимо, различая исправленные и новые ошибки. Ничего не считать собранным без логов Unreal Build Tool/UHT. Все выводы с датой заносить в подробную карточку; короткую карточку обновлять после неё; сводную таблицу №15 и состояние №14 синхронизировать; в конце записать срез в №13 и прочитать обратно.

**Границы карточек:** подробная = воспроизводимость, паспорт запуска, версии, фактический ход раундов, точные дефекты и доказательства; короткая = что получилось, что не получилось, балл /10 или `null`, следующий шаг. Короткую карточку готовим как потенциальные данные будущего интерфейса Web Alarm Ultra, но **интеграция пока отсутствует**.

**Нумерация и связи:** №14 → `17_KAT-Coder-V2.5` → `17.1_KAT-Coder-V2.5_кратко`. Для Qwen3.6 по прямому решению владельца выбран №19 и №19.1 (№18 уже занимает техническая документация); в дальнейшем номер и `.1` только с разрешения владельца; не создавать `.2`, `.3` для каждого раунда. №15 и №16 — самостоятельные общие ветки №14. Архивы `Reports/*.txt` вне графа, оригиналы не редактировать.

**Текущий пример:** KAT-Coder R1 = `REVISE`, R2 = `REVISE`; реальная компиляция и runtime = `NOT RUN`, оценка = `null`. Это не шаблон ожидаемого результата для остальных моделей.

**Правило терминов:** `GENERATED` (ответ), `SELF-REVIEW` (утверждение модели), `INDEPENDENT TEXT REVIEW` (проверка текста), `BUILD PASS` (лог сборки), `RUNTIME PASS` (работающий сценарий); `REVISE` (есть дефекты), `NOT RUN` (не запускалось), `UNKNOWN` (нет данных). Частичное исправление не равно успешному раунду, а отсутствие оценки не равно 0/10.

## 1. Паспорт прогона — заполнять до ответа

| Поле | Значение |
| --- | --- |
| Идентификатор прогона | `[MODEL]-[TEST]-[YYYYMMDD]-[RUN]` |
| Дата/время с часовым поясом | UNKNOWN |
| Модель и точная ревизия | UNKNOWN |
| Формат весов, квантование, происхождение | UNKNOWN |
| Движок/версия/ветка | UNKNOWN |
| Машина выполнения; CPU/GPU; RAM/VRAM | UNKNOWN |
| Параметры: `ctx`, `ngen`, `temperature`, `top_p` и другие | UNKNOWN |
| Работающая сессия/изоляция; выбранная модель | UNKNOWN |
| Точная версия задания, SHA-256 текста, если рассчитан | МАЯК-47 v1.0 |
| Время первого токена, общая длительность, токены/с | NOT MEASURED |
| Инструменты / доступ к файлам / разрешения | NONE / UNKNOWN |
| Компилятор/версия UE, если проводилась сборка | NOT RUN |

**Важно:** не смешивать сервер `DESKTOP-KT4G5SM` и компьютер агента `DESKTOP-SC96D3U`. Тестовые файлы живут в данном vault только как отчёты; их наличие не доказывает запуск проекта UE5.

## 2. Фиксируемые раунды

**Раунд 1 — первая попытка.** Ссылка на исходный неизменённый ответ (Markdown); техническое review с точными фрагментами и классификацией ошибок.

**Раунд 2 — самостоятельное исправление.** Отдельный исходный prompt исправления; ссылка на неизменённый второй ответ; таблица `ошибка → замечена моделью? → исправлена? → новая регрессия?`. По возможности одинаковая подсказка/степень помощи моделям.

**Реальные испытания.** Отдельно `BUILD` (UHT, C++), `RUNTIME` (клавиша E, расстояния 425/426 см, смещение +35 Z, первые 0.35 с, отсутствие Tick), `TOOL USE` (если разрешено), журналы и время.

## 3. Таблица проверки 12 пунктов

Для каждого исходного требования №1–12 фиксировать: `PASS (код+доказательство) / PARTIAL / FAIL / NOT RUN / UNKNOWN`, расположение реализации, дефект и идентификатор evidence. **Статус из отчёта модели не равен независимому статусу.**

## 4. Состав обязательного отчёта модели

- Оригинальный prompt и ответ без переписывания задним числом.
- Собственные замечания модели и полная исправленная версия кода.
- Проверенные/непроверенные утверждения, явно `NOT RUN` для неисполненной компиляции.
- Итоговые плюсы, дефекты, риск регрессий.
- Баллы по методике Оценка LLM или `ОЦЕНКА ОТЛОЖЕНА`.

## 5. Создание нового кейса

Для каждой тестируемой модели создать **два связанных документа**: подробное досье `[номер]_[название LLM].md` и краткую карточку `[номер].1_[название LLM]_кратко.md` (пример: `17_KAT-Coder-V2.5.md` → `17.1_KAT-Coder-V2.5_кратко.md`). В подробном досье хранить технический паспорт, раунды, выявленные ошибки, исправления, независимую проверку и выводы. В краткой карточке — текущий статус, балл /10 (или отсутствие оценки), сильные и слабые стороны, следующий шаг; её данные планируется показывать в Web Alarm Ultra. В графе добавить **только** связь `14_Тестирование_LLM` → досье модели и связь досье → краткая карточка; не соединять краткую карточку напрямую с 14, 15 или 16. Общий рейтинг поддерживать в `15_Оценка_LLM`. Полные исходные ответы сохранять как неизменяемый архив доказательств без отдельных видимых узлов. Не создавать новые узлы для каждого раунда или ревью. После каждого принятого результата синхронизировать досье, краткую карточку и рейтинг; оригиналы ответов не переписывать.
