**PARTIAL / REVIEW PENDING · LOCAL ONLY · CLEANUP PENDING.** Реализация и приёмка в изолированном стенде выполнены. Инференс на рабочей Qwen, CPU/CUDA-бенчмарк и эксплуатационная приёмка установленных Client/Manager остаются открыты.

## DONE

Client хранит именованные чаты по постоянному UUID. Чаты с одним Manager, слотом и моделью имеют независимые истории и настройки. Переназначение сохраняет переписку. При недоступности модели или Manager история остаётся доступной. Интерфейс чатов отделён от каталога и управления слотами.

SQLite v2 переносит группы Manager/slot/model/instance в архивные чаты. Копия исходной базы получает отдельное имя, проверяется через SQLite quick_check и остаётся в защищённом каталоге. Схема и перенос подтверждаются в одной транзакции. Таблица reasoning хранит старые и новые рассуждения. История позволяет открыть reasoning отдельной реплики. Контекстный запрос читает текст отдельно и формирует объекты только с role/content. Ответ с одним reasoning отображается в истории, его пустая текстовая реплика пропускается в контексте.

Сброс ставит границу после текущей истории. Более новые реплики участвуют в контексте, а старые остаются в переписке до явного возврата. Очистка скрывает переписку выбранного чата и допускает восстановление из этой же базы. Восстановление сохраняет границу контекста до явного возврата. Удаление с отдельным подтверждением удаляет чат, сообщения, reasoning и метрики из активной базы. Ранее сделанная резервная копия имеет собственный срок хранения.

Stream сохраняет ответ при подтверждённом завершении. Обработаны неполный поток, отказ, отмена и повторный запрос. После завершения Client проверяет Manager сразу, затем до четырёх раз с интервалами 120, 300, 650 и 1250 мс между проверками. Активный запрос показывает «Модель отвечает». Слот, возвращающий busy, остаётся занят. При ручном скролле вверх прирост reasoning и ответа оставляет пользователя на месте.

У новых реплик сохранены UTC-метки начала и окончания запроса в Client. Время старой реплики показывается как неизвестное. Браузер измеряет время от отправки до первого reasoning/delta, длительность после первого фрагмента и полное время. Client сохраняет свои измерения по завершённым, отменённым и ошибочным запросам. Список измерений привязан к чату и фильтруется по модели и CPU/CUDA. Режим внешнего экземпляра может быть неизвестен Manager.

## EVIDENCE

Шлюз работающей Qwen запущен установленным лаунчером Colibri v2.1.0. Через WinRM прочитаны SHA-256 шлюза и метаданные /health. SHA совпал с исходником, использованным в пробах. Health вернул qwen36, окно 16 384, максимум 16 384 и scheduler capacity 1. В работающую модель отправлялись только диагностические чтения. `../WorkEvidence/summary.json`

В openai_server.py метод chat_completion берёт body.messages, рассчитывает preserve_thinking, вызывает renderer и передаёт prompt движку. conversation_cache_slot выбирает оптимизацию для переданного префикса. qwen36.c токенизирует сформированный prompt и сопоставляет токены с KV-префиксом. В проверенной трассе нет идентификатора разговорной истории или добавления прошлых сообщений вне payload. В Colibri есть opt-in compaction с кешем резюме переданного префикса, а COLI_COMPACT=1 может сделать её поведением по умолчанию. Новый Manager явно передаёт context_compaction=off. При сочетании нового Client со старым Manager это зависит от настройки шлюза.

Qwen3.6 рендерит роли в ChatML. Наличие прежнего reasoning меняет default preserve_thinking и помещает его в блоки think предыдущих ответов. В двух опытах совпадающий с рабочим исходник шлюза отрендерил синтетические A–F. Для подсчёта использована локальная копия работающего qwen36.exe с тем же tokenizer.json в режиме TOK_ONLY. Он возвращает токены до model_init, без загрузки весов. `../WorkEvidence/colibri-ab.py`

В изученном native Qwen prompt_tokens берётся из токенизации полного prompt, включая шаблон и совпавший KV-префикс. Completion_tokens соответствует генерируемым engine-токенам до EOS, включая reasoning и служебные границы, если движок их генерирует. Шлюз разделяет reasoning и видимый ответ после токенизации. Usage публикует вход и совокупный выход. Отдельного проверенного счётчика reasoning в API нет. При неизвестном usage Client показывает «нет данных». Маршрутная скорость делит подтверждённый completion_tokens на длительность запроса Manager → Colibri вместе с подготовкой. Чистую скорость декодера интерфейс не выводит.

## PROBLEMS / QUESTIONS

- Неудачная legacy-отправка в первом unit-цикле создавала пустую базу. Исправлено. Статический тест отдельного окна теперь проверяет постоянный ID.
- Первый portable запуск с нестандартным --config-dir вызвал видимое окно Invalid protected Client directory. Скрипт ACL создавал стандартный каталог, хотя Python получил другой путь. Теперь Python передаёт целевой путь, а перед созданием проверяет его компоненты. Прежний вызов скрипта без параметра работает со стандартным каталогом. Повторный EXE прошёл полный сценарий.
- Повторный Chrome-прогон выявил гонку scroll при возврате в активный чат. При смене чата позиция теперь устанавливается сразу после построения DOM.
- Следующий прогон поймал запоздалое событие от программного скролла после роста ответа. Client теперь отслеживает изменение scrollTop отдельно от изменения высоты контента. В параллельном QA также зарегистрирован WinError 10053 в старом тесте pairing; последовательный повтор полного Manager suite прошёл.
- UI показывает последние 100 реплик выбранного чата и последние 25 измерений. SQLite хранит историю целиком. Отмена в интерфейсе доступна для потоковой отправки.
