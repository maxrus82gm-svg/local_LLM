## 1. Рабочие правила Codex

1. **Источник работы:** только БЛОК 1 с задачей, назначенной владельцем, либо его прямое адресное поручение с указанными границами. План, NEXT, сообщение «можно будет» или отсутствие задач — не назначение. Поправки после назначения фиксировать как AMENDMENT с датой, не заменяя первоначальный текст.
2. **Вход:** изучить этот раздел, БЛОК 1, разрешённые источники из read matrix постановки, нужные узкие фрагменты `00_Старт.md`, `02_Назначение_проекта.md`, `03_Архитектура.md` и `13_Тактический_контекст.md` **только когда это прямо предусмотрено scope**. Не читать автоматически чужие карточки, общие архивы или весь реестр. Если источник недоступен — сообщить `SOURCE UNAVAILABLE`.
3. **Границы:** выполнять только перечисленные read/write/test-действия. Без отдельного разрешения не трогать Git/GitHub, системные настройки, работающие процессы/загрузки, модели и веса, сеть, чужие файлы и рабочее хранилище. Техническая доступность не означает разрешения. Особое согласование требуется для остановки загрузок и любых установок/удалений.
4. **Инженерный подход:** сначала установить существующее состояние, проверить переиспользование и соседние ограничения; выбрать минимальное достаточное решение. Делать проверяемые изменения, фиксировать подтверждённые факты и отдельно гипотезы. Не расширять TASK из-за попутной находки.
5. **Проверки:** выполнять оговорённые тесты в разрешённой среде, указывать команды/результаты и `PASS / FAIL / SKIP / NOT RUN`; для документации проверять содержимое, ссылки, отсутствие потерянных записей и граф Obsidian. Самопроверка Codex — доказательство исполнителя, **не** независимая приёмка.
6. **Сдача:** сохранить полный отчёт и, когда согласовано, manifest/evidence в постоянном разрешённом месте. Ответ в чате содержит `DONE / CHANGED / DIFF / PROBLEMS / QUESTIONS`, фактический статус, тесты, риски, DOC IMPACT, адрес отчёта и предложенный NEXT. Не выдавать черновик за завершённый отчёт.
7. **Приёмка и история:** ChatGPT-координатор отдельно проверяет результат, сохраняет полную исходную постановку и отчёты, заполняет персональную историю, общий реестр/хронологию и тактический контекст. Codex **не пишет себе independent PASS** и не изменяет личный архив.
8. **Ротация:** после отчёта/evidence Codex переносит дословную TASK из БЛОКА 1 в 1.1 со статусом SUBMITTED / REVIEW PENDING и освобождает БЛОК 1. Независимая приёмка не требуется для ротации. Перед заменой прежнего 1.1 его полный оригинал и AMENDMENT должны иметь проверенный постоянный адрес (Git SHA + №05/09); иначе ARCHIVE BLOCKED. БЛОК 4 и архивы меняет только координатор.

### Среда Codex/Desktop — обязательная проверка путей

Codex работает **на компьютере владельца**, поэтому обращается к файлам Ultra LLM по сетевому корню `\\192.168.0.77\Server\Ultra_LLM` (например, к `Documents`, `Colibri`, `Base_LLM\Models`). Путь `C:\Server\Ultra_LLM` — локальный **на сервере**, не предполагаемый диск Codex. Он допустим внутри BAT, который будет исполняться на сервере, но файл BAT агент редактирует через UNC. Запуск BAT с UNC на компьютере агента не запускает его на сервере. Указать фактическую машину, путь, доступ, права, место выполнения и тестовый scope; если нет права удалённого запуска — `NOT RUN`. Правило — `000_Задачи для агента.md` → §3.1.

## 2. Что должна содержать назначенная TASK

- **TASK ID / дата / исполнитель / цель и критерий результата.**
- **Read matrix:** точные пути, разделы и необходимость чтения.
- **Write scope:** перечисление разрешённых каталогов/файлов; что менять нельзя.
- **Ограничения/разрешения:** процессы, сеть, Git, модели, личные данные и системные действия отдельно.
- **План доказательств:** тесты, критерии приёмки, обработка ошибок и границы проверки.
- **Отчётность:** место постоянного отчёта, минимальный состав `DONE/CHANGED/DIFF/PROBLEMS/QUESTIONS`.
- **Границы завершения:** что считается результатом, что требует нового решения владельца.

**Если TASK неполная или противоречит правилам:** уточнить только блокирующие вопросы; не расширять разрешения предположением.

Развернуть актуальную версию Ultra LLM Web Client с реализованными P0 streaming/reasoning и P1 каталогом моделей/динамическими слотами так, чтобы пользователь запускал её через **тот же существующий ярлык Ultra LLM Client**.

Обеспечить переносимость сборки на другие компьютеры Windows x64.

Результатом должна стать реально работающая программа, а не только исходники, mock, скриншот или офлайн-тесты.

## 4. Этап A — определить фактически запускаемую версию

Провести read-only диагностику:

1. Проверить состояние Git и исходников.
    
2. Проверить наличие и состав установленного `M:\UltraLLM_Client`.
    
3. Прочитать текущий VBS-запускатор.
    
4. Проверить Target, Arguments и WorkingDirectory рабочего ярлыка.
    
5. Определить полный путь реально запущенного `UltraLLMClient.exe`.
    
6. Определить, какой процесс обслуживает локальный Web Client.
    
7. Сопоставить его ресурсы с текущими исходниками Git.
    
8. Проверить, не открыт ли старый процесс с прежней версией UI.
    
9. Проверить, достаточно ли уже имеющейся сборки для обновления без пересборки.
    

**Обязательно:** не принимать наличие новых файлов в Git за факт обновления установленной программы.

Если актуальная проверенная portable-сборка уже существует, разрешено переиспользовать её вместо ненужной пересборки.

## 5. Этап B — подготовить актуальный portable release

При необходимости собрать новую переносимую версию с использованием существующего `Build-Portable.ps1` и согласованного Python/PyInstaller toolchain.

Новая сборка должна включать:

- `UltraLLMClient.exe`;
    
- весь необходимый каталог `_internal`;
    
- актуальные веб-ресурсы;
    
- P0 streaming/reasoning Client;
    
- P1 каталог моделей и динамические слоты;
    
- работающий VBS-запускатор;
    
- механизм установки ярлыка;
    
- зависимости и обязательные лицензии;
    
- SHA-256 manifest;
    
- ZIP-архив для переноса.
    

**Не переносить в релиз:** пользовательские токены, `managers.json`, TLS-приватные ключи, историю SQLite, логи, пароли, веса моделей или конфигурацию конкретного компьютера.

Создать уникальный каталог нового выпуска в:

`M:\UltraLLM_Builds\Release`

Не перезаписывать старые архивы.

Рабочие пользовательские профили и история остаются в `%LOCALAPPDATA%\UltraLLM\Client` без очистки или переноса.

## 8. Этап E — обновить установленный Client

Владелец разрешил обновление **локального Client** с созданием резервной копии и проверкой.

Разрешается штатно завершить только подтверждённый собственный процесс Web Client. Не завершать другие приложения и не использовать глобальный kill по имени процесса.

После безопасного завершения:

1. Сохранить действующую папку.
    
2. Установить новый полностью проверенный portable release в постоянный каталог:
    

`M:\UltraLLM_Client`

3. Проверить все файлы по SHA-256.
    
4. Сохранить неизменным существующий ярлык, если он корректен.
    
5. Запустить именно существующий рабочий ярлык.
    
6. Проверить путь реально запущенного EXE.
    
7. Убедиться, что браузер открыл именно обновлённый Client.
    
8. Проверить отсутствие второго конкурирующего процесса.
    
9. При ошибке выполнить rollback к R4.
    

Не устанавливать программу в очередной каталог `R5`, `TEST` или `CHATxx` с перенаправлением рабочего ярлыка.

Постоянный каталог остаётся `M:\UltraLLM_Client`.

## 10. Переносимость на другие компьютеры

Сборка должна поддерживать сценарий:

**Скопировать ZIP → распаковать в произвольный каталог → запустить установщик ярлыка → открыть Web Client.**

Требования:

- Windows x64;
    
- отсутствие необходимости устанавливать Python;
    
- отсутствие обязательного диска `M:`;
    
- отсутствие жёсткого IP сервера;
    
- локальный HTTP только на `127.0.0.1`;
    
- настоящий Manager исключительно по доверенному HTTPS;
    
- персональная регистрация каждого Client;
    
- собственные секреты, профили и история на каждом компьютере;
    
- корректная установка ярлыка без изменения других ярлыков.
    

Стандартный ярлык Windows `.lnk`, VBS-запускатор и EXE допустимо сохранить. Менять расширения только при подтверждённой технической необходимости.

На другом ПК должна запускаться та же программа, но доступ к Manager предоставляется отдельно. Не копировать туда действующий пользовательский токен домашнего компьютера.

## 11. Жёсткие ограничения

**Запрещено:**

- изменять удалённую ветку `main` или `GPT`, выполнять push/merge/force-push;
    
- самовольно изменять архитектуру Manager;
    
- обновлять серверный `UltraLLM_Manager_LIVE`;
    
- останавливать или перезапускать Colibri1/Qwen3.6;
    
- вмешиваться в Valheim;
    
- менять серверные TLS-секреты и ACL;
    
- запускать другие LLM;
    
- менять настройки firewall и WinRM;
    
- менять существующий ярлык на временный путь;
    
- переписывать или удалять пользовательские чаты;
    
- устанавливать неподтверждённую или непрошедшую тесты сборку.
    

Если для исправления паковки нужны изменения исходников, разрешены минимальные правки только в Client и его тестах. Показать diff, провести повторные проверки и явно согласовать фиксацию исходников до установки. Не устанавливать релиз с неучтёнными изменениями.

При неустранимом блокере — не рисковать рабочей R4, сохранить её и сдать отчёт.

## 12. Приёмочные критерии

**PASS** только если:

1. Новый релиз соответствует актуальному проверенному исходному коду.
    
2. Полная сборка проверена.
    
3. Резервная копия R4 создана и проверена.
    
4. Программа установлена по постоянному адресу.
    
5. Старый ярлык запускает новую установленную программу.
    
6. Браузер показывает новый Client, а не тестовую заглушку и не старый процесс.
    
7. Реальный Manager отображается без потери существующего подключения.
    
8. История и пользовательский профиль сохранены.
    
9. Повторный запуск не создаёт дублей.
    
10. Подготовлен переносимый ZIP для другого компьютера.
    
11. Есть проверенный сценарий возврата к R4.
    
12. Защищённые процессы и серверные настройки не изменены.
    

Частично выполненные проверки отражать отдельно. Не объявлять реальную работу новых серверных функций подтверждённой по mock-тестам.

## 5. P1 — каталог, слоты и несколько одинаковых LLM

### 5.1. Интерфейс

В каждой карточке Manager предусмотреть две логические области.

**Верхняя:** список доступных моделей, обнаруженных через существующий доверенный каталог и проверенную локальную инвентаризацию. Разделять «файлы обнаружены», «движок совместим», «готова к запуску» и «уже работает».

**Нижняя:** рабочие слоты.

- Для текущего Manager первоначально отображать три сконфигурированных слота.
    
- Кнопка «+ Добавить слот» создаёт новый управляемый слот.
    
- Для каждого слота выбирается доступная модель.
    
- Внутри слота располагаются START CPU, START CUDA, STOP и фактическое состояние.
    
- Отображать привязанный экземпляр, его режим, выбранную LLM и причину недоступности операции.
    
- Не вводить глобальную константу «максимум 3».
    
- Слоты и выбор должны сохраняться при предусмотренном перезапуске Manager/Client.
    
- Оформление будущих расширенных описаний LLM — не приоритет этой TASK.
    

Добавление слота в интерфейсе должно соответствовать настоящему безопасному серверному контракту, а не только новой строке DOM.

### 5.2. Повторные экземпляры одинаковых моделей

Удалить архитектурный запрет запуска второго экземпляра по совпадению `model_key`, включая текущую проверку `model_already_managed`.

Вместо уникальности модели гарантировать уникальность `instance_id`, слота, порта, управляющих объектов и рабочих данных.

Допустить:

- Qwen3.6 CPU и Qwen3.6 CUDA одновременно;
    
- два экземпляра одной модели в CPU;
    
- два или более CUDA-экземпляра одной либо разных моделей, если установленный runtime и физические ресурсы позволяют.
    

Не обещать, что несколько CUDA дадут ускорение, или что веса обязательно будут совместно размещены в VRAM.

Сохранить общий read-only доступ к весам, но изолировать runtime, состояние, логи, временные файлы, mutex и Windows Job Object каждого экземпляра.

SQLite должен атомарно резервировать **экземпляр и конкретный слот**, а не единственное использование имени модели.

### 5.3. Ресурсы без искусственных запретов

Исторические параметры FIRST_CPU_14G (фиксированный Job cap 14 ГиБ, admission 24 ГиБ, watchdog 10 ГиБ) не должны действовать как универсальная политика для всех будущих моделей.

Переработать их в явные настройки и политику предупреждений с учётом типа модели и реальных возможностей Colibri.

**Порог 10 ГиБ свободной RAM по умолчанию — предупреждение, а не автоматический запрет.** Владелец может изменить порог и осознанно подтвердить рискованный запуск.

Показывать ожидаемый остаток RAM/VRAM, степень достоверности оценки и возможное влияние на другие модели и Valheim.

При этом не разрешать обход настоящей несовместимости runtime/CUDA, недоступных портов, системных запретов ОС, отсутствия прав или проверок принадлежности процессов.

Не отключать защиту от случайного завершения Colibri1 и чужих процессов.

### 5.4. Динамическое создание слота

Сервер должен выдавать безопасный новый `slot_id`, подходящий порт, уникальные пути и сохранённую конфигурацию.

## 4. Отчёт исполнителя — минимальная форма

```text
TASK ID:
RESULT: RESULT READY / PARTIAL / BLOCKED / DRAFT
DONE: что фактически получилось
CHANGED: точные изменённые файлы
DIFF: краткая суть изменений / адрес diff
TESTS: PASS / FAIL / SKIP / NOT RUN + evidence
PROBLEMS: ошибки, ограничения и неподтверждённое
QUESTIONS: блокирующие вопросы, если остались
DOC IMPACT: что требуется обновить в документации
REPORT: постоянный проверяемый путь
NEXT: предложение, не новая назначенная TASK
```

**Правило передачи между чатами:** живое состояние и подтверждённые NEXT сохраняет ChatGPT в `13_Тактический_контекст.md` после каждого результата или значимого решения; переписка и память исполнителя не являются постоянным архивом.
